g3 세션 수집과 bitrate 오염 분석

2.4GHz 독립 세션 g3을 수집해 기존 배포 모델을 평가하자, 다른 세션보다 심각(L3) precision이 유독 낮게 나왔다. 원인을 추적하다 학습 데이터의 sta_tx_bitrate_mean 오염과 평가 방식의 낙관성이라는 두 가지 구조적 문제를 확인했고, 평가를 leave-one-session-out(LOSO)으로 바꿔 기준선을 다시 세웠다. 이 문서는 그 과정과 결과, 남은 문제를 정리한다.

한 줄 결론. g3의 낮은 precision은 모델이 배운 bitrate 규칙("낮으면 혼잡, 높으면 심각")이 세션이 바뀌면 깨지기 때문인 것으로 보이지만, 오염된 런을 단순히 빼면 혼잡 학습 데이터가 같이 사라져 오히려 나빠진다. 세션 단위로 평가하면 세션 평균 정확도 88.4%, L3 recall 77~78%, precision 83~84%이고, 이 수치는 "심각이 어떤 유형이냐"(occupancy 주도 vs loss·latency 주도)에 더 크게 좌우된다. 후속으로 링크 상태를 바꿔 수집한 g4·g5와 7세션 LOSO 결과는 10절에 있다.

  • AP 크래시 판정 정정: kneepkt500 중 AP 무응답을 처음에 "정체"로 판단했으나, 이후 AP 가동 시간이 5분으로 초기화돼 있어 실제 재부팅이었다. 회복 뒤의 응답(유선 ping 정상)을 근거로 삼은 것이 오판이었다. 크래시 판정은 가동 시간 초기화와 DHCP 임대 소실로 해야 한다. (kneelo 1차의 100초 무응답은 가동 시간이 이어져 재부팅이 아니었다.)
  • bitrate 고착 재발: AP 재부팅 뒤 노트북 tx bitrate가 1~9Mbps로 고착 → Wi-Fi 어댑터 끄기/켜기(관리자 권한)로 해소.

06평가 방식을 바꾼 이유

기존 평가는 창(12행씩 묶음)을 무작위로 train/val/test에 나눈다. 이웃 창은 행 11개를 공유하므로 test 창의 쌍둥이가 train에 들어 있다. 그래서 in-dist 92~93%는 본 적 있는 런의 이웃 구간을 맞히는 능력까지 포함한 낙관적 수치다. 실제로 독립 세션에서는 78~84%로 내려간다.

  • 행을 섞은 뒤 창을 만드는 것은 안 된다: 창이 시계열이 아니게 되어 추세(rssi_delta, 이동평균)와 배포 때의 입력(연속 12폴링)이 달라진다.
  • 런 단위 분할만으로도 부족하다: 같은 세션의 다른 런은 같은 날·같은 AP 상태·같은 링크 조건을 공유한다. bitrate 고착이 바로 이 세션 수준의 특수성이었다.
  • leave-one-session-out: 세션(8/28, 9/1, g1, g2, g3)을 하나씩 통째로 빼고 나머지로 학습해 빠진 세션으로 테스트한다. 검증은 학습 세션마다 마지막 런을 통째로 분리해 쓴다. LOSO는 성능 추정용이고, 배포 모델은 고른 설계로 모든 세션을 합쳐 다시 학습한 EE 모델 하나다.

한계. g1·g2·g3는 같은 집·같은 밤(g2·g3는 연속)이라 하나를 빼도 나머지가 학습에 남는다. 진짜 다른 날은 8/28과 9/1뿐이라 g fold 수치는 낙관적이다.

088/28 recall이 낮은 이유 — 심각의 유형

세션별 심각(L3) 창을 원인 유형으로 나눴다. 8/28의 심각은 occupancy 주도가 40%뿐이고 51%는 occupancy가 임계(75%) 미만인데 측정된 loss·latency로 붙은 심각이다(테스트에 쓴 품질 통과 런 105창 기준). 나머지 세션은 79~87%가 occupancy 주도다.

occupancy 주도occ 미달 + 측정된 loss/latencyocc 미달 + 프로브 stale
  • AP 텔레메트리는 채널 점유율을 직접 보므로 occupancy 주도 심각은 잘 잡고(recall 82~92%), occupancy가 낮은 채 victim QoS만 깨지는 심각은 못 잡는다. 이전 분석의 유형별 recall(26~41%)과 방향이 같다.
  • 즉 g1·g2·g3의 높은 recall은 이 세션들의 심각이 대부분 occupancy 주도라서 얻은 값일 수 있다. 8/28은 심각의 절반 가까이가 어려운 유형이라 recall이 낮은 것으로 보인다.
  • 이는 세션 구성(부하 프로파일)에 따라 성능이 크게 달라진다는 뜻이므로, 발표·보고서에서 하나의 recall 수치를 내세우기보다 유형별로 함께 제시해야 한다.

한계. 8/28 fold의 낮은 recall이 "유형 구성 때문"이라는 설명은 구성 비교에서 나온 것이고, 유형별로 통제해서 재학습한 검증은 하지 않았다.

09종합 — 지금 보이는 문제점과 다음 단계

문제점

  1. 학습 데이터의 bitrate 오염과 라벨 편중: 행의 53%가 고착 런이고, 혼잡 라벨의 70%가 거기서 나왔다. 단순 제외는 혼잡 예시를 없애 오히려 나빠진다.
  2. 평가의 낙관성: 창 단위 분할은 이웃 창 유출을 포함한다. 세션 단위로 봐야 새 날에 대한 성능이 나온다.
  3. 세션 다양성 부족: 세션이 5개뿐이고 g1·g2·g3는 같은 집·같은 밤이다. 학교 등 다른 장소는 확인하지 못했다.
  4. 심각 유형의 한계: occupancy가 낮은 채 QoS만 깨지는 심각은 AP 텔레메트리로 잘 안 보인다(recall 40% 안팎). feature 설계만으로 풀리지 않을 수 있는 관측 한계다.
  5. 수집 환경 불안정: AP 크래시·정체, bitrate 고착, 러너의 미감지(서버 다운, Pi 파일 이어 붙음)가 반복돼 깨끗한 데이터를 모으기 어렵다.

다음 단계 (제안)

  • 재수집 범위를 좁힌다: 전체가 아니라, bitrate가 깨끗한 조건에서 혼잡 라벨과 경계 구간(점유율 55~75%), 그리고 occupancy 미달 loss·latency 주도 심각(8/28 유형)을 다른 날·다른 조건에서 모은다. 러너에 서버 생존 점검, Pi 파일 정리, bitrate 고착 감지를 넣는다.
  • 평가 기준을 LOSO로 고정하고, 이 기준에서 EE Fixed·Dynamic·SDN도 다시 비교한다(지금은 Baseline만).
  • bitrate 유지 방식: 오염 런은 제외 대신 학습 가중치를 낮추거나 재수집분으로 대체해 혼잡 예시를 보존하는 방안을 검토한다.
  • 배포 모델: 고른 설계로 모든 세션을 합쳐 학습한 EE 모델 하나. 성능은 LOSO 평균(세션별 범위 포함)으로 인용한다.

러너 보완 (run_profile.sh)

  • iperf3 서버 점검: 시작 전 5201/5202/5203을 확인하고 죽어 있으면 재기동한다(실패 시 중단). 시험에서 의도적으로 내린 서버가 자동 복구됐다.
  • Pi 잔여 정리: 같은 이름의 옛 CSV를 _prev_시각으로 옮기고 남은 수집기 프로세스를 종료한다(이어 붙음 방지). g4 재수집에서 동작을 확인했다.
  • AP 재부팅 감지: AP uptime을 10초마다 기록하고 값이 줄면 크래시로 판정해 부하를 중단한다. 실제 크래시로는 아직 시험하지 못했다.
  • 기존 bitrate 고착·품질 게이트는 유지하고, 세션 드라이버는 게이트 실패를 경고로 두고 계속 진행하는 변형을 쓴다.
