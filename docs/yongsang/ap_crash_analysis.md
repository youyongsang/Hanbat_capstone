# AP(Opal GL-SFT1200) 반복 크래시 원인 분석

2026-08-23 밤 ~ 2026-08-24 새벽 세션에서 `ap_metrics_v2`(2차) label 3 데이터를 더 모으려고 여러 부하 조합을 시도하며 관찰한 크래시 패턴을 정리한다.

**2026-08-24 오후 세션 기준 최신 결론**: 아래 3차 가설("폰이 송신하면 크래시")과 그로부터 파생됐던 "191 개별 하드웨어 문제" 결론은 **오후 세션에서 반증에 가깝게 뒤집혔다.** S26/191 둘 다 단독으로는 40~150Mbps까지 크래시 없이 완주했고, 191+S26을 동시에 붙였을 때만 크래시가 발생했다 — **"몇 대가 동시에 붙어있는가"(다중 station)가 다시 핵심 변수 쪽으로 재선회했다.** 상세는 맨 아래 "추가 검증(2026-08-24 오후)" 섹션 참고. 아래 1~4차 가설 변화 과정은 그 결론에 이르기까지의 역사적 기록으로 남겨둔다.

## 가설의 변화

두 번 정정했다.

1. **1차 가설(기각): 잦은 재연결(reconnect churn)이 원인이다.** UDP 손실률을 계속 갱신하려고 2~5초마다 iperf3를 재접속시켰는데, 이게 AP에 부담을 준다고 생각했다. → 재연결 루프를 완전히 제거한 시도(2대, 100Mbps)도 여전히 ~22초 만에 크래시해서 기각.
2. **2차 가설(기각): 동시 station이 2개 이상이면 크래시한다.** 3대/2대 조합은 전부 20~60초 안에 죽었고, 1대만 쓴 시도는 재연결 유무와 무관하게 훨씬 오래 버텼다(70~100Mbps로 2~5분 완주). → 그런데 라즈베리파이를 유선 서버로 써서 "노트북 1대(무선)→파이(유선)" 구조로 150Mbps까지 시도했더니 전혀 안 죽었고, 반대로 "폰 1대(무선)→파이(유선)"는 station이 똑같이 1개인데도 거의 즉시 크래시했다. station 개수만으로는 설명이 안 됨.
3. **현재 가설: 폰이 능동적으로(트래픽을 만들어) 송신할 때 크래시한다.** 노트북이 송신자면 목적지가 무엇이든(폰이든 유선 파이든), 전송률이 얼마든(150Mbps까지 확인) 안정적이었다. 폰이 송신자면 목적지·전송률과 무관하게 거의 즉시 크래시했다.

## 핵심 비교

| 구성 | station 수 | 송신자 | 결과 |
|---|---:|---|---|
| 폰 2~3대 동시(폰↔노트북 또는 폰↔폰) | 2~3 | 폰 (일부) | 20~60초 내 크래시 (일부 예외 있음, 아래 참고) |
| 노트북 → 폰(무선) | 1 | 노트북 | 안정적 (70~100Mbps, 2~5분 완주) |
| 노트북 → 파이(유선) | 1 | 노트북 | 안정적 (150Mbps까지, 3분 완주) |
| **폰 → 파이(유선)** | **1** | **폰** | **거의 즉시 크래시** (수집 행 0개) |

3번째와 4번째 행이 결정적이다 — station 수·목적지가 완전히 동일한데 송신자만 바뀌었고, 결과가 정반대다.

## 예외: 첫 시도는 다대여도 완주했다

3대(폰) 동시, 40Mbps, 90초 시도는 완주했다(재연결 루프 포함 상태였음에도). 이건 그날 AP를 켠 뒤 **첫 부하 시도**였다는 공통점이 있다 — 이후 재시도할수록 버티는 시간이 급격히 짧아진 패턴(90초 → 40초 → 18초 → 22초)과 맞물려, "폰 송신 자체가 위험"이라는 가설 위에 "반복 사용 누적 피로"가 겹쳐진 것으로 보인다. 즉 변수가 하나가 아니라 최소 두 개(송신자 종류 + 누적 사용) 겹쳐 있을 가능성이 있다.

## 부가 발견: 유선 파이 구조는 안전하지만 label 3을 못 만든다

노트북→파이 150Mbps 시도에서 `channel_occupancy_percent`가 100%까지 여러 번 찍혔는데도 `congestion_score`는 최대 0.646에서 막혔다(label 3 문턱 0.75 미달). 유선 목적지는 무선 충돌/재전송이 거의 없는 "깨끗한" 경로라 `retry_failed_score`, `jitter_score`가 낮게 유지되기 때문으로 추정된다. 즉 **안전성(노트북 송신)과 label 3 생성 능력(무선 경합 필요)이 트레이드오프 관계**다.

## 추가 검증 (2026-08-24 아침): 다른 폰(S26)으로 교체 → 크래시 재현 안 됨

새로 구매한 폰 S26(`192.168.8.103`)을 송신자로 세워 재검증했다. station 수(2대, 노트북+S26)·목적지(이 노트북, 무선)·전송률(20Mbps→40Mbps)이 이전 191 폰의 즉시 크래시 조건과 비슷했는데도 20Mbps 120초, 40Mbps 90초 모두 완주했고 물리적 재부팅이 필요한 크래시는 없었다. 40Mbps 구간에서 AP가 SSH 폴링에 ~30초 응답 지연을 보인 적은 있지만 station 연결은 유지된 채 자연 복구됐다 — 예전의 "SSID 자체가 증발" 패턴과는 다른 경미한 증상이다.

**해석 갱신(당시)**: "폰이 능동적으로 송신하면 크래시한다"는 3번째 가설이 S26에서는 재현되지 않았다. **"191 폰 개별 하드웨어/드라이버 문제였을 가능성"이 "폰 송신 자체가 위험"이라는 가설보다 유력해졌다.** 다만 70~100Mbps 이상 고부하에서도 S26이 계속 안정적인지는 아직 확인 전이라, 이 가설을 완전히 확정하기엔 이르다. 상세 로그는 `.work-log/current.md`의 "2026-08-24 아침 세션" 참고.

**→ 이 해석은 아래 오후 세션 검증으로 뒤집혔다.**

## 추가 검증 (2026-08-24 오후): S26/191 각각 단독 램프업 + 다중 station 콤보 — "191 개별 문제" 반증, 다중 station 가설로 재선회

목적지는 항상 이 노트북(무선), AP는 세션 시작 시 재부팅 직후 상태(uptime 5분)에서 출발.

- **S26 단독**: 70M(90초)·100M(180초) 완주, 크래시 없음. label 3은 0개(occupancy 100% 포착되지만 retry/jitter가 동시에 안 터짐, congestion 최대 0.692)
- **191 단독**: 40M→70M→100M→120M→150M **다섯 단계 전부 완주, 크래시 없음**. 40~120M 네 단계 모두 label 3 1개씩 생성(150M만 예외). retry_delta 최대치는 S26(25,422)과 191(23,487)이 비슷한 수준 — "191이 유독 노이즈가 많다"기보다 occupancy 포화와 retry/jitter 폭주가 같은 순간에 겹치는 빈도가 191에서 더 높았던 것으로 보임
- **191+S26 동시(다중 station)**: 2회 시도해서 1승 1패. 191=60M/S26=100M(90초) 조합은 완주(label 3 1개 포함, connected_clients=3, 결합 처리량 최대 88.9Mbps). 곧이어 191=70M/S26=100M 조합은 **SSH 완전 타임아웃으로 크래시**(throughput이 점진적 저하 없이 급격히 0 근처로 붕괴한 뒤 응답 없음, 물리 재부팅 필요)

**해석 갱신(최신)**: 191이 이번엔 5단계 연속 생존했다는 것 자체가 "191 개별 하드웨어 문제" 결론과 정면으로 배치된다. 반면 오늘 유일하게 크래시가 난 경우는 다중 station 조합이었다 — **"몇 대가 동시에 붙어있는가"가 크래시의 핵심 변수라는 2차 가설(위에서 한 번 기각됐던) 쪽으로 다시 무게가 실린다.** 다만 콤보가 1승 1패라 표본이 매우 적어 확정할 단계는 아니다. 상세 로그는 `.work-log/current.md`의 "2026-08-24 오후 세션" 참고.
