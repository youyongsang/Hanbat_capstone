# AP(Opal GL-SFT1200) 반복 크래시 원인 분석

2026-08-23 밤 ~ 2026-08-24 새벽 세션에서 `ap_metrics_v2`(2차) label 3 데이터를 더 모으려고 여러 부하 조합을 시도하며 관찰한 크래시 패턴을 정리한다.

**2026-08-27 세션 기준 최신 결론**: 아래 3차 가설("폰이 송신하면 크래시")과 그로부터 파생됐던 "191 개별 하드웨어 문제" 결론은 **오후~저녁 세션에서 반증에 가깝게 뒤집혔다.** S26/191 둘 다 단독으로는 40~150Mbps까지 크래시 없이 완주했고, 191+S26을 동시에 붙였을 때만 불안정성이 나타났다 — 한때 **"몇 대가 동시에 붙어있는가"(다중 station)가 다시 핵심 변수 쪽으로 재선회**했으나, 2026-08-26 저녁~밤 세션에서 콤보 안정성이 **두 폰의 와이파이 재연결 여부**에 크게 좌우되는 것이 드러나면서 "다중 station 자체"보다 **개별 폰의 와이파이 연결 상태 / Wi-Fi capture effect(신호가 강한 S26이 채널을 독점하고 신호가 약한 191이 굶는 비대칭)**가 더 유력한 설명으로 부상했다. 스위트스팟은 **191=60M/S26=60M(2~7분)**이 기준선이지만, 8/26 밤 세션에서 **정확히 대칭인 75M/75M**도 label 3 생성 후보로 떠올랐다(단 재현성 불완전). 부하 상한은 확실하다 — **80/80은 10분 시도에서 완전 크래시(물리 재부팅 필요)**, 60/60도 **500초를 넘기면 완전 크래시**를 재현했다(안전 구간 대략 300~420초). 2026-08-27 세션에서는 실기기 없이 **SSH 폴링 자기참조 지연 문제를 지속 SSH 세션(`APPoller`)으로 전환**하는 코드 조치를 했다(미검증). 상세는 맨 아래 "추가 검증"/"추가 조치" 섹션들 참고. 아래 1~5차 가설 변화 과정은 그 결론에 이르기까지의 역사적 기록으로 남겨둔다.

## 가설의 변화

네 번 정정했다.

1. **1차 가설(기각): 잦은 재연결(reconnect churn)이 원인이다.** UDP 손실률을 계속 갱신하려고 2~5초마다 iperf3를 재접속시켰는데, 이게 AP에 부담을 준다고 생각했다. → 재연결 루프를 완전히 제거한 시도(2대, 100Mbps)도 여전히 ~22초 만에 크래시해서 기각.
2. **2차 가설(기각 → 부분 부활): 동시 station이 2개 이상이면 크래시한다.** 3대/2대 조합은 전부 20~60초 안에 죽었고, 1대만 쓴 시도는 재연결 유무와 무관하게 훨씬 오래 버텼다(70~100Mbps로 2~5분 완주). → 그런데 라즈베리파이를 유선 서버로 써서 "노트북 1대(무선)→파이(유선)" 구조로 150Mbps까지 시도했더니 전혀 안 죽었고, 반대로 "폰 1대(무선)→파이(유선)"는 station이 똑같이 1개인데도 거의 즉시 크래시했다. station 개수만으로는 설명이 안 됨. (→ 5차에서 다중 station이 다시 유력해졌다가, 6차에서 "폰 와이파이 상태"로 재해석됨)
3. **3차 가설(약화): 폰이 능동적으로(트래픽을 만들어) 송신할 때 크래시한다.** 노트북이 송신자면 목적지가 무엇이든(폰이든 유선 파이든), 전송률이 얼마든(150Mbps까지 확인) 안정적이었다. 191 폰이 송신자면 목적지·전송률과 무관하게 거의 즉시 크래시했다. → 아침 세션에 다른 폰(S26)으로 교체하니 재현 안 됨.
4. **4차 가설(반증): 191 폰 개별 하드웨어/드라이버 문제였을 가능성.** S26이 같은 조건에서 안정적이라 유력해 보였으나, 오후 세션에서 191을 40M→70M→100M→120M→150M 다섯 단계 연속으로 돌려도 크래시가 한 번도 안 났다 — 5단계 연속 생존 자체가 "191 개별 문제"와 정면 배치됨.
5. **5차 가설(재선회 후 약화): 다시 다중 station이 핵심 변수.** S26/191 둘 다 단독으로는 40~150Mbps까지 완주했지만 191+S26 동시 부하에서만 불안정성이 나타났다. → 그런데 8/26 저녁~밤 세션에서 **같은 콤보 조합이 어떤 날은 크래시하고 어떤 날은 5~7분씩 깨끗하게 완주**했고, 그 차이가 "두 폰의 와이파이를 시작 전에 재연결했는가"와 강하게 상관됨.
6. **현재 가설: 개별 폰의 와이파이 연결 상태 / Wi-Fi capture effect.** 콤보 불안정성의 실제 변수는 "몇 대인가"보다 "각 폰이 AP 와이파이에 제대로·대칭적으로 붙어있는가"로 보인다. 신호가 강한 S26이 채널을 거의 독점하고 신호가 약한 191이 굶는 비대칭(capture effect)이 반복 관측됨 — 191은 그동안 ping 지연이 S26보다 계속 크고 불안정했다(RSSI 열세 추정). 여기에 "부하가 80/80 이상이거나 500초 이상 길면 그와 무관하게 완전 크래시"라는 상한 조건이 겹친다.

## 핵심 비교

| 구성 | station 수 | 송신자 | 결과 |
|---|---:|---|---|
| 폰 2~3대 동시(폰↔노트북 또는 폰↔폰) | 2~3 | 폰 (일부) | 20~60초 내 크래시 (일부 예외 있음, 아래 참고) |
| 노트북 → 폰(무선) | 1 | 노트북 | 안정적 (70~100Mbps, 2~5분 완주) |
| 노트북 → 파이(유선) | 1 | 노트북 | 안정적 (150Mbps까지, 3분 완주) |
| **폰 → 파이(유선)** | **1** | **폰** | **거의 즉시 크래시** (수집 행 0개) |

3번째와 4번째 행이 결정적이다 — station 수·목적지가 완전히 동일한데 송신자만 바뀌었고, 결과가 정반대다.

## 예외: 첫 시도는 다대여도 완주했다

3대(폰) 동시, 40Mbps, 90초 시도는 완주했다(재연결 루프 포함 상태였음에도). 이건 그날 AP를 켠 뒤 **첫 부하 시도**였다는 공통점이 있다 — 이후 재시도할수록 버티는 시간이 급격히 짧아진 패턴(90초 → 40초 → 18초 → 22초)과 맞물려, "폰 송신 자체가 위험"이라는 가설 위에 "반복 사용 누적 피로"가 겹쳐진 것으로 보인다. 즉 변수가 하나가 아니라 최소 두 개(송신자 종류 + 누적 사용) 겹쳐 있을 가능성이 있다.

## 부가 발견: 유선 파이 구조는 안전하지만 label 3을 못 만든다

노트북→파이 150Mbps 시도에서 `channel_occupancy_percent`가 100%까지 여러 번 찍혔는데도 `congestion_score`는 최대 0.646에서 막혔다(label 3 문턱 0.75 미달). 유선 목적지는 무선 충돌/재전송이 거의 없는 "깨끗한" 경로라 `retry_failed_score`, `jitter_score`가 낮게 유지되기 때문으로 추정된다. 즉 **안전성(노트북 송신)과 label 3 생성 능력(무선 경합 필요)이 트레이드오프 관계**다.

## 추가 검증 (2026-08-24 아침): 다른 폰(S26)으로 교체 → 크래시 재현 안 됨

새로 구매한 폰 S26(`192.168.8.103`)을 송신자로 세워 재검증했다. station 수(2대, 노트북+S26)·목적지(이 노트북, 무선)·전송률(20Mbps→40Mbps)이 이전 191 폰의 즉시 크래시 조건과 비슷했는데도 20Mbps 120초, 40Mbps 90초 모두 완주했고 물리적 재부팅이 필요한 크래시는 없었다. 40Mbps 구간에서 AP가 SSH 폴링에 ~30초 응답 지연을 보인 적은 있지만 station 연결은 유지된 채 자연 복구됐다 — 예전의 "SSID 자체가 증발" 패턴과는 다른 경미한 증상이다.

**해석 갱신(당시)**: "폰이 능동적으로 송신하면 크래시한다"는 3번째 가설이 S26에서는 재현되지 않았다. **"191 폰 개별 하드웨어/드라이버 문제였을 가능성"이 "폰 송신 자체가 위험"이라는 가설보다 유력해졌다.** 다만 70~100Mbps 이상 고부하에서도 S26이 계속 안정적인지는 아직 확인 전이라, 이 가설을 완전히 확정하기엔 이르다. 상세 로그는 `.work-log/current.md`의 "2026-08-24 아침 세션" 참고.

## 추가 검증 (2026-08-24 오후): S26/191 각각 단독 램프업 + 다중 station 콤보 — "191 개별 문제" 반증, 다중 station 가설로 재선회

목적지는 항상 이 노트북(무선), AP는 세션 시작 시 재부팅 직후 상태(uptime 5분)에서 출발.

- **S26 단독**: 70M(90초)·100M(180초) 완주, 크래시 없음. label 3은 0개(occupancy 100% 포착되지만 retry/jitter가 동시에 안 터짐, congestion 최대 0.692)
- **191 단독**: 40M→70M→100M→120M→150M **다섯 단계 전부 완주, 크래시 없음**. 40~120M 네 단계 모두 label 3 1개씩 생성(150M만 예외). retry_delta 최대치는 S26(25,422)과 191(23,487)이 비슷한 수준 — "191이 유독 노이즈가 많다"기보다 occupancy 포화와 retry/jitter 폭주가 같은 순간에 겹치는 빈도가 191에서 더 높았던 것으로 보임
- **191+S26 동시(다중 station)**: 2회 시도해서 1승 1패. 191=60M/S26=100M(90초) 조합은 완주(label 3 1개 포함, connected_clients=3, 결합 처리량 최대 88.9Mbps). 곧이어 191=70M/S26=100M 조합은 **SSH 완전 타임아웃으로 크래시**(throughput이 점진적 저하 없이 급격히 0 근처로 붕괴한 뒤 응답 없음, 물리 재부팅 필요)

**해석 갱신(오후)**: 191이 이번엔 5단계 연속 생존했다는 것 자체가 "191 개별 하드웨어 문제" 결론과 정면으로 배치된다. 반면 오늘 유일하게 크래시가 난 경우는 다중 station 조합이었다 — **"몇 대가 동시에 붙어있는가"가 크래시의 핵심 변수라는 2차 가설(위에서 한 번 기각됐던) 쪽으로 다시 무게가 실린다.** 다만 콤보가 1승 1패라 표본이 매우 적어 확정할 단계는 아니다. 상세 로그는 `.work-log/current.md`의 "2026-08-24 오후 세션" 참고.

## 추가 검증 (2026-08-24 저녁): 재부팅 후 콤보 부하 스위핑 — "60/60이 스위트스팟"

오후 세션의 크래시(191=70M/S26=100M) 이후 AP를 물리 재부팅하고, 콤보 부하 크기를 낮춰가며 재검증했다.

- **40M/60M(90초)**: 완주, label 3 0개. 부하는 낮췄는데 폴링 지연 70초 스파이크가 오히려 발생 — 부하 크기와 안정성이 단순 비례하지 않음을 시사
- **60M/60M(120초)**: 완주, **label 3 4개/41행(9.8%)** — 지금까지 콤보 중 최고 성과. 폴링 지연 최대 13초로 양호
- **80M/80M(150초)**: 완주(물리 재부팅까지는 안 감)했지만 label 3 0개, retry는 최고치(66,870)까지 튀어도 occupancy(56~67%)와 안 맞물림. **폴링 지연 110초 스파이크**(SSH가 최대 12.5초간 연결 자체 실패) — 완전 크래시(SSH 영구 불통)와 정상 사이의 중간 심각도 증상을 처음 명확히 관측
- **60M/60M을 10분(600초)으로 연장**: 완주, label 3 2개/76행(2.6%) — **비율로는 2분 버전(9.8%)보다 낮음**. 중반부(3~7분대)에 폴링 지연이 계속 이어지다 94초 스파이크까지 나옴

**해석 갱신(최신)**: 부하를 올릴수록(80/80) 나빠지고, **60M/60M(2분 내외)이 안정성·label 3 생성력 둘 다에서 스위트스팟**이다. 지속시간을 늘리는 것도 역효과 — 장시간 노출은 크래시 리스크(폴링 지연 누적)만 키우고 label 3 비율은 오히려 낮춘다. "SSH 완전 끊김 후 자연 복구"라는 중간 심각도 증상이 확인됐으므로, 크래시를 단순 이분법(완주 vs 물리 재부팅 필요)으로만 보지 말고 지연 정도를 스펙트럼으로 추적해야 한다. 상세 로그는 `.work-log/current.md`의 "2026-08-24 저녁 세션" 참고.

7. **테스트 종료 보고를 받으면 iperf3 서버/수집기 프로세스를 즉시 종료할 것** — 새벽 세션에서 두 번이나 방치돼서 유휴 시간이 raw CSV에 몇십 분~1시간씩 섞여 들어감(데이터 품질엔 문제없지만 비효율). 자동종료 타이머를 쓸 경우 반드시 "실제 부하 시작 시점" 기준으로 걸 것 — 수집기 시작 시점 기준으로 걸면 오발 종료 위험(8/26 새벽 rep6에서 실제로 발생)
8. **`-b ??M` 대안 부하 방법을 시도해서 label 3을 노릴 것 — 아래 "부하 생성 방법 대안" 섹션 참고.** AP 크래시 천장(80/80·500초) 때문에 "제공 부하를 더 키우는" 방향은 막혀 있으므로, 5GHz/80MHz는 그대로 두고 **(a) 소패킷 UDP로 PPS·airtime을 올리고 (b) 동일 채널 간섭원으로 RF 환경을 나쁘게** 만드는 방향이 다음 우선순위. 채널 크리플(2.4GHz 전환)은 배포 regime과 안 맞아 지양. Opal 소비자 AP 한계도 감안 — 더 나은 AP 확보가 정공법.
9. 호중에게 이 분석을 공유 — 펌웨어 업데이트나 대체 장비 확보 가능성 문의.
10. **다음 세션 최우선(신규): 지속 SSH 세션 방식(`APPoller`)을 실기기로 검증** — 정상 스트리밍, 폴링 지연 감소 여부, 재연결 루프 안정성 확인.
11. **유선 관리채널 분리 실행(2026-08-27 설계 확정, 방법 2부터 시작)** — collector를 노트북(이더넷 포트 없음)에서 라즈베리 파이(이더넷+WiFi 내장, headless 운용)로 옮긴다. 구조: 폰↔AP(무선, 부하) / AP→파이 iperf3 수신(무선 유지 필수 — 유선으로 옮기면 위 "부가 발견" 섹션처럼 congestion_score가 0.75 문턱을 못 넘어 label 3을 못 만든다) / 파이→AP SSH 관리(신규 유선). 분리 방법은 (a) 라우팅 규칙(`ip route add 192.168.8.1/32 dev eth0`, 간단하지만 같은 서브넷 ARP 꼬임 가능) vs (b) Opal `/etc/config/network`에서 LAN 포트를 별도 서브넷으로 분리(깔끔하지만 기존 설정 백업 필요) — **(b)부터 시도하기로 결정**, 안 되면 (a)로 폴백. 상세 논의는 `.work-log/current.md` 2026-08-27 세션 참고.

## 부하 생성 방법 대안 — 소패킷 + RF 환경 열화 (2026-08-27 논의, 미실험)

### 왜 필요한가

**연결되는 상위 질문**: 이 프로젝트가 답해야 하는 건 "occupancy만으로는 안 잡히는 혼잡(경합·간섭·재전송 주도)을 조기종료 LSTM이 얼마나 정확히 잡는가"다(`docs/yongsang/congestion_label_redesign.{md,html}` §1·§3, 실측 대조는 `project/results/yongsang/ap_v2_redesign2_threshold_comparison_k3m2_archived_20260902.txt`(k3m2 시절 마지막 실행, k2m2로 재실행 안 함)). 그런데 현재 label 3 샘플이 거의 다 occupancy=100% 순간이라 모델이 지름길만 학습했을 수 있다 — 아래 방법들의 목적은 **occupancy가 아니라 retry/jitter가 주도하는 label 2/3 샘플을 확보**하는 것이다.

현재 부하는 "다중 기기 × `iperf3 -u -b ??M`(기본 ~1470B UDP 프레임)"뿐이다. 두 가지 한계:

1. **label 3이 잘 안 나온다** — occupancy(점유율)는 100%까지 포화되는데 `tx_retries_per_s`/`jitter_ms`가 같은 순간에 같이 안 튀어서 congestion_score가 0.75 문턱을 못 넘는 경우가 잦다.
2. **부하를 키우면 AP가 크래시한다** — 80/80·500초 이상은 완전 크래시로 확정. "제공 부하(offered load)를 더 키우는" 방향은 막혀 있다.

**핵심 재해석(2026-08-27)**: 목표는 "낮은 throughput"이 아니다. label 3을 만드는 건 **높은 PPS(초당 프레임 수)·airtime 점유**와 **열악한 RF 환경**이다. 실험실은 RF가 깨끗해서 재전송이 잘 안 생기는데, 실제 공장은 금속·다중경로·용접 EMI·밀집 AP 때문에 **훨씬 낮은 부하에서도 retry/jitter가 터진다** — 이게 lab에서 label 3이 안 나오는 근본 이유다. 따라서 (a) 프레임을 잘게 쪼개 PPS를 올리고, (b) RF 환경을 의도적으로 나쁘게 만드는 두 축이 정답이고, **채널을 크리플(2.4GHz 강제 등)하는 방향은 배포 regime과 안 맞아서 지양**한다. throughput_mbps가 낮아지는 건 무해하다 — §07 분석대로 throughput_score는 label 2/3를 거의 구분 못 한다.

> **주의 — Opal은 소비자용 AP다.** 크래시 천장(80/80·500초)은 물리 법칙이 아니라 GL-SFT1200이라는 싸구려 장비의 한계다. *현실적인* 데이터가 목적이면 더 나은 산업/기업용 AP 확보(호중 문의, next-steps 참고)가 정공법이고, 아래 방법들은 그 사이 label 3 표본을 보충하는 augmentation으로 본다.

### 방법 1 — 소패킷 UDP 플러드 (5GHz/80MHz 그대로, AP 설정 무변경)

```powershell
# 폰별 서버(각 폰): iperf3 -s -p 5201 (191) / iperf3 -s -p 5202 (S26)
# 송신(각 폰 Termux 또는 수집 담당이 원격 실행), 대칭으로:
iperf3 -u -c 192.168.8.226 -p 5201 -l 250 -b 25M -t 300
iperf3 -u -c 192.168.8.226 -p 5202 -l 250 -b 25M -t 300
```

- 802.11은 프레임당 고정 오버헤드(PHY 프리앰블 + DIFS + 랜덤 백오프 + SIFS + ACK)가 커서, **250B 프레임은 1470B 대비 같은 Mbps에서 airtime 5~6배**. occupancy 100% + 충돌/재전송이 훨씬 낮은 합계 throughput에서 나온다.
- **"소패킷 = 비현실적"이 아니다.** 산업 무선 트래픽의 지배적 패턴이 소패킷이다 — PROFINET/EtherNet-IP 주기 I/O(수십~수백 바이트, 1~4ms 주기), OPC-UA pub/sub, MQTT 텔레메트리, 측위 비콘, PTT 음성. 공장 바닥의 수백 대가 소형 주기 프레임을 뿌리는 게 "채널은 꽉 찼는데 총 throughput은 중간"인 혼잡을 만든다. 대용량 blast(`-b`)보다 오히려 더 현실적이다.
- **밴드·채널폭은 5GHz/80MHz 그대로 두고 패킷 크기만** 바꾼다 → 배포 regime을 안 바꾼다.
- `-l`은 **200~400에서 조정**. 너무 작으면(<150) 폰(Termux) CPU가 PPS 병목이 되어 오히려 airtime이 안 오른다 — `iperf3` 서버 출력의 실제 pps/throughput으로 병목 여부 확인.

### 방법 2 — 동일 채널 간섭원 (실제 공장 다중 AP 환경 모사)

측정에 안 쓰는 기기(여분 폰/노트북/두 번째 AP)로 같은 채널을 점유시킨다 — 유튜브 4K 재생, 별도 `iperf3`, 또는 두 번째 AP를 같은 채널에서 방송.

- 이게 **실제 다중 AP 공장의 co-channel interference 그 자체**다. lab에 없는 "열악한 RF 환경"을 가장 현실적으로 재현하는 방법.
- 이 기기는 congestion_score 입력 feature에 안 들어간다(`connected_clients`는 제외 컬럼) → CCA-busy·경합·재전송만 추가하고 라벨 계산은 오염 안 됨.
- 2대 동시 송신 콤보(다중 station)보다 크래시 리스크가 낮을 수 있다.

### 방법 3 — 낮은 MCS 고정 / RSSI 약화 (거리·장애물 모사)

기기를 AP에서 멀리 두거나, `iw`로 MCS/레거시 레이트를 낮게 고정하거나, 금속판 뒤에 둔다.

- 매 프레임 on-air 시간↑ → 점유율·충돌·재전송↑. regime을 밴드/채널폭만큼 크게 바꾸지 않으면서 retry를 올린다.
- 191의 RSSI 열세를 역이용할 수도 있다(capture effect와 상충하지 않게 확인).

### 방법 4 (참고) — 애플리케이션 실측형 부하

"산업 무선 혼잡" 서사에 가장 부합하고 발표 설득력이 크다.

- **VoIP류**(20ms마다 초소형 RTP 패킷): 몇 Mbps로 airtime 포화, AP 부담 최소. SIPp+RTP 또는 다수 G.711 스트림.
- **BitTorrent 대용량 다운로드** 2~3대 동시: 다수 연결·소패킷·양방향·uTP → 교과서적 혼잡 패턴.
- **다중 4K 영상 스트리밍**: 적응형 비트레이트·재전송 → 현실적인 jitter/loss.
- pktgen/trafgen/MGEN 같은 커널·연구용 생성기는 Windows 노트북에선 안 되고 Pi(Linux)에서 — 파이 무선 송신은 아직 미검증이니 소규모부터.

### 보류 — 채널폭 20MHz / 2.4GHz 전환

- **2.4GHz 전환은 하지 않는다.** 밴드가 바뀌면 용량·간섭·feature 분포가 통째로 달라지고, 공장의 고대역 애플리케이션(머신비전, 영상 감시)은 5GHz를 쓴다.
- **20MHz(5GHz 유지)**는 다중 AP 채널 재사용·결정론 목적으로 산업에서도 쓰이긴 하지만, 80MHz와 feature 분포가 달라지므로 **배포 타깃 AP의 채널폭을 먼저 확정한 뒤 일관되게** 가야 한다. 지금은 미확정이니 보류.

### 데이터 관리 주의

- 패킷 크기·RF 조건을 바꾸면 `throughput_mbps`·`channel_occupancy_percent`·`tx_retries_per_s` 범위가 달라진다 → `prepare_ap_metrics_dataset.py` 재변환 시 `scaler_params.json`이 재적합되며, **기존 데이터와 한 학습셋에 섞는 게 타당한지 팀 논의 필요**(분포 shift).
- 새 `scenario` 이름으로 구분 수집: 예 `combo_smallpkt_l250_s21_s26`, `combo_smallpkt_cochannel_s21_s26`. 기존 `combo_s21_60m_s26_60m*`와 섞이지 않게.
- 소패킷만 / 간섭원만 각각 단독 baseline을 먼저 잡고 나서 조합할 것.
