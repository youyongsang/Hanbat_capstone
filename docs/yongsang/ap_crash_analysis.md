# AP(Opal GL-SFT1200) 반복 크래시 원인 분석

2026-08-23 밤 ~ 2026-08-24 새벽 세션에서 `ap_metrics_v2`(2차) label 3 데이터를 더 모으려고 여러 부하 조합을 시도하며 관찰한 크래시 패턴을 정리한다.

**2026-08-26 새벽 세션 기준 최신 결론**: 아래 3차 가설("폰이 송신하면 크래시")과 그로부터 파생됐던 "191 개별 하드웨어 문제" 결론은 **오후~저녁 세션에서 반증에 가깝게 뒤집혔다.** S26/191 둘 다 단독으로는 40~150Mbps까지 크래시 없이 완주했고, 191+S26을 동시에 붙였을 때만 불안정성이 나타났다 — **"몇 대가 동시에 붙어있는가"(다중 station)가 다시 핵심 변수 쪽으로 재선회했다.** 저녁 세션에서 재부팅 후 콤보 부하를 스위핑해서 **191=60M/S26=60M(2분 내외, 이후 5~7분까지 확장 검증)이 스위트스팟**임을 확인했고, 그 위(80/80)나 장시간(10분)은 오히려 더 불안정했다. **2026-08-26 새벽 세션에서 이 스위트스팟의 지속시간 상한을 500초까지 밀어봤다가 진짜 완전 크래시(ping 100% loss, SSH 완전 타임아웃, 물리 재부팅 필요)를 재현**했다 — 60/60의 안전 구간은 대략 **300~420초까지**로 보인다. 상세는 맨 아래 "추가 검증" 섹션들 참고. 아래 1~4차 가설 변화 과정은 그 결론에 이르기까지의 역사적 기록으로 남겨둔다.

## 가설의 변화

두 번 정정했다.

1. **1차 가설(기각): 잦은 재연결(reconnect churn)이 원인이다.** UDP 손실률을 계속 갱신하려고 2~5초마다 iperf3를 재접속시켰는데, 이게 AP에 부담을 준다고 생각했다. → 재연결 루프를 완전히 제거한 시도(2대, 100Mbps)도 여전히 ~22초 만에 크래시해서 기각.
2. **2차 가설(기각): 동시 station이 2개 이상이면 크래시한다.** 3대/2대 조합은 전부 20~60초 안에 죽었고, 1대만 쓴 시도는 재연결 유무와 무관하게 훨씬 오래 버텼다(70~100Mbps로 2~5분 완주). → 그런데 라즈베리파이를 유선 서버로 써서 "노트북 1대(무선)→파이(유선)" 구조로 150Mbps까지 시도했더니 전혀 안 죽었고, 반대로 "폰 1대(무선)→파이(유선)"는 station이 똑같이 1개인데도 거의 즉시 크래시했다. station 개수만으로는 설명이 안 됨.
3. **현재 가설: 폰이 능동적으로(트래픽을 만들어) 송신할 때 크래시한다.** 노트북이 송신자면 목적지가 무엇이든(폰이든 유선 파이든), 전송률이 얼마든(150Mbps까지 확인) 안정적이었다. 폰이 송신자면 목적지·전송률과 무관하게 거의 즉시 크래시했다.

## 핵심 비교

| 구성 | station 수 | 송신자 | 결과 |
|---|---:|---|---|
| 폰 2~3대 동시(폰↔노트북 또는 폰↔폰) | 2~3 | 폰 (일부) | 20~60초 내 크래시 (일부 예외 있음, 아래 참고) |
| 노트북 → 폰(무선) | 1 | 노트북 | 안정적 (70~100Mbps, 2~5분 완주) |
| 노트북 → 파이(유선) | 1 | 노트북 | 안정적 (150Mbps까지, 3분 완주) |
| **폰 → 파이(유선)** | **1** | **폰** | **거의 즉시 크래시** (수집 행 0개) |

3번째와 4번째 행이 결정적이다 — station 수·목적지가 완전히 동일한데 송신자만 바뀌었고, 결과가 정반대다.

## 예외: 첫 시도는 다대여도 완주했다

3대(폰) 동시, 40Mbps, 90초 시도는 완주했다(재연결 루프 포함 상태였음에도). 이건 그날 AP를 켠 뒤 **첫 부하 시도**였다는 공통점이 있다 — 이후 재시도할수록 버티는 시간이 급격히 짧아진 패턴(90초 → 40초 → 18초 → 22초)과 맞물려, "폰 송신 자체가 위험"이라는 가설 위에 "반복 사용 누적 피로"가 겹쳐진 것으로 보인다. 즉 변수가 하나가 아니라 최소 두 개(송신자 종류 + 누적 사용) 겹쳐 있을 가능성이 있다.

## 부가 발견: 유선 파이 구조는 안전하지만 label 3을 못 만든다

노트북→파이 150Mbps 시도에서 `channel_occupancy_percent`가 100%까지 여러 번 찍혔는데도 `congestion_score`는 최대 0.646에서 막혔다(label 3 문턱 0.75 미달). 유선 목적지는 무선 충돌/재전송이 거의 없는 "깨끗한" 경로라 `retry_failed_score`, `jitter_score`가 낮게 유지되기 때문으로 추정된다. 즉 **안전성(노트북 송신)과 label 3 생성 능력(무선 경합 필요)이 트레이드오프 관계**다.

## 추가 검증 (2026-08-24 아침): 다른 폰(S26)으로 교체 → 크래시 재현 안 됨

새로 구매한 폰 S26(`192.168.8.103`)을 송신자로 세워 재검증했다. station 수(2대, 노트북+S26)·목적지(이 노트북, 무선)·전송률(20Mbps→40Mbps)이 이전 191 폰의 즉시 크래시 조건과 비슷했는데도 20Mbps 120초, 40Mbps 90초 모두 완주했고 물리적 재부팅이 필요한 크래시는 없었다. 40Mbps 구간에서 AP가 SSH 폴링에 ~30초 응답 지연을 보인 적은 있지만 station 연결은 유지된 채 자연 복구됐다 — 예전의 "SSID 자체가 증발" 패턴과는 다른 경미한 증상이다.

**해석 갱신(당시)**: "폰이 능동적으로 송신하면 크래시한다"는 3번째 가설이 S26에서는 재현되지 않았다. **"191 폰 개별 하드웨어/드라이버 문제였을 가능성"이 "폰 송신 자체가 위험"이라는 가설보다 유력해졌다.** 다만 70~100Mbps 이상 고부하에서도 S26이 계속 안정적인지는 아직 확인 전이라, 이 가설을 완전히 확정하기엔 이르다. 상세 로그는 `.work-log/current.md`의 "2026-08-24 아침 세션" 참고.

- rep9 도중 폰 쪽에서 "unable to read from stream socket: Try again" 에러가 떴지만, connected_clients=3이 57행 내내 유지되고 AP SSH도 정상이었음 — **8/25 새벽 세션에서 이미 기록된 "스트림 종료 시점 근처의 무해한 폰 클라이언트 에러"라는 패턴이 재확인됨**
- **rep10에서 지속시간을 500초로 늘려봤다가 진짜 완전 크래시가 재현됨**: throughput이 84.86Mbps에서 급격히 붕괴 → retry_delta 10,935→33,288→39,060으로 폭주 → latency/jitter 0으로 죽음 → SSH 완전 타임아웃(ping 100% loss, 자연 복구 안 됨, 물리 재부팅 필요). 8행에서 중단(label 3 0개)
- **결론**: 60/60 스위트스팟의 안전 구간은 무한정이 아니라 **대략 300~420초까지**로 보인다 — 500초는 그 경계를 넘어서 예상보다 빨리 완전 크래시로 이어짐. 다음 시도는 500초 이상으로 더 늘리지 말고 300~420초 구간을 반복하는 쪽을 권장. 상세 로그는 `.work-log/current.md`의 "2026-08-26 새벽 세션" 참고.

## 추가 조치 (2026-08-27): SSH 폴링 자기참조 지연 — 지속 SSH 세션으로 전환(코드 변경, 실기기 미검증)

`.work-log/current.md` 8/26 밤 세션에서 "설계 메모, 코드 변경 없음"으로 남겨뒀던 실시간 폴링 문제에 대한 첫 코드 조치. 근본 원인은 `collect_metrics.py`가 매 루프(약 0.5~1초 간격)마다 **새 SSH 프로세스**를 띄워 TCP+SSH 핸드셰이크를 반복했다는 것 — 이 관리 트래픽이 측정 대상과 같은 무선 채널을 그대로 타고 가서, 채널이 혼잡할수록 SSH 핸드셰이크 자체도 같이 느려지는 자기참조적 구조였다. 폴링 지연 스파이크(최대 156초)와 완전 크래시(rep10, 500초 시도) 둘 다 이 구조와 무관하지 않을 가능성이 있다.

- **변경**: `get_ap_metrics()`(루프마다 새 SSH 접속) → `APPoller` 클래스로 교체. 원격에서 `iw station dump`/`survey dump`를 무한루프로 도는 셸 명령 하나를 SSH 세션 **1개**로 띄우고, 표준출력을 백그라운드 스레드가 스트리밍으로 읽어 사이클 단위로 캐시한다. 메인 루프는 그 캐시에서 새 사이클을 기다리기만 하므로(로컬 sleep, 네트워크 호출 없음) 더 이상 느려진 SSH 응답에 동기적으로 블록되지 않는다. 연결이 끊기면 스레드가 자동 재연결하고(`poller.reconnects`로 횟수 추적), 종료 시 로그에 재연결 횟수를 출력한다.
- **CSV 스키마/스코어링 로직은 변경 없음** — `parse_station_info`/`parse_channel_occupancy`/`calculate_scores` 등은 그대로 재사용, 데이터 수집 의미론(1행 = 1회 실제 AP 샘플)도 유지된다.
- **아직 실기기로 검증 안 됨** — 이 세션에서는 AP에 붙어있지 않아 문법 검사(`py_compile`)만 확인했다. 다음 AP 세션에서 반드시: (1) 지속 SSH 연결이 정상적으로 station/survey 데이터를 스트리밍하는지, (2) 콤보 부하 중 폴링 지연 스파이크가 실제로 줄어드는지, (3) AP가 죽었을 때 재연결 루프가 무한 재시도로 CPU/네트워크를 낭비하지 않는지 확인할 것.
- **이 조치가 다루지 않는 부분**: 관리 트래픽이 여전히 같은 무선 채널을 타고 간다는 근본 구조는 그대로다(핸드셰이크 반복만 없앤 것). 완전한 해결(AP 온보드 로컬 수집, 또는 유선 관리채널 분리)은 여전히 미결 — 아래 "다음 검증 방향" 참고.
