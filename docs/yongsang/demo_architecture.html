Demo architecture · 2026-10-08 (10-09 갱신)

데모 사이트 구조

공유기(AP)가 보는 정보만으로 AI가 와이파이 혼잡을 실시간 판단하고, 2.4GHz가 막히면 5GHz로 옮겼을 때 어떻게 달라지는지 한 화면에서 보여 주는 시연 사이트다. 이 문서는 무엇이 어디서 돌고, 데이터가 어떻게 흐르고, 왜 이렇게 설계했는지를 정리한다.

1. 한눈에

2개 화면demo.html 한 대역 화면 · demo_dual.html 2.4GHz·5GHz 비교 화면
서버 2개대역마다 하나: 2.4GHz :8000 · 5GHz :8001 (같은 코드, --band만 다름)

폰당 30M시연 부하: 2.4GHz 심각 92% vs 5GHz 경고 92% (10-06 리허설)

시연 흐름은 세 단계다.

  1. 2.4GHz에서 혼잡 만들기 — 관객이 버튼을 누르면 폰 두 대가 실제로 데이터를 보낸다. 왼쪽 칸이 혼잡·심각으로 오르고 "다른 대역으로 옮겨야 해요" 경보가 뜬다.
  2. 5GHz로 옮기기 — 시연자가 폰의 와이파이를 5GHz 이름으로 바꾼다(실제 현장에선 AP의 밴드 스티어링이 자동으로). 화면이 폰 위치를 스스로 찾는다.
  3. 같은 부하 다시 걸기 — 오른쪽 5GHz 칸은 같은 양에도 정상~경고에 머문다.

모델이 보는 것은 AP 텔레메트리 7개뿐이다(처리량·점유율·재전송·RSSI 3종·전송 속도). 정답 라벨을 만들 때 쓴 victim 프로브·ping은 시연 중엔 없다 — 그래서 "공유기 정보만으로 판단"이라는 서사가 성립한다.

3. 데이터 흐름

3-1. 추론 루프 (서버마다, 매 폴링)

AP 폴링 — 지속 SSH(APPoller, collect_metrics.py 재사용)로 자기 대역 인터페이스(wlan0 또는 wlan1)를 약 0.5~1초마다 읽는다. 15초 넘게 응답이 없을 때만 "AP 응답 없음"을 띄운다.
7-feature 계산 — 처리량(rx+tx 바이트 증가분), 점유율(survey busy/active, 3폴링 중앙값), 재전송 비율(최근 5폴링), RSSI·RSSI 변화·RSSI 5폴링 평균, 송신 중인 기기의 tx bitrate 평균. 수집기와 같은 식.
정규화 → 창 12 — 대역별 스케일러(min-max)로 0~1, 최근 12폴링을 한 창으로 묶는다. 창이 차기 전엔 "측정 준비 중".
ONNX INT8 Early Exit 추론 — unified 그래프(If 노드) 한 번 호출. 확신이 충분하면 1·2번째 출구에서 일찍 끝난다. 출력: 4단계 확률 + 출구 번호.
후처리 — 원시 판정(raw_label)은 그대로 두고, 화면 표시용으로만 같은 단계가 연속될 때 바꾼다(서버 5폴링, 비교 화면 3폴링). 전환 판단기(SwitchAdvisor)는 최근 3폴링 중 2번 심각이면 "전환 필요"를 켜고 30폴링 동안 심각이 없으면 끈다. 다운링크 우세(처리량 많은데 점유율 낮음)면 "판단 불확실" 표시.
SSE 방송 — 상태 JSON을 /events로 모든 브라우저에 보낸다. 정답 비교용 truth도 같이 싣는다.

3-2. 부하 (버튼 → 폰)

브라우저 버튼(폰당 10/20/30/40M)
  → POST /load {phone, rate, packet_size:1400, duration_s:60}   ※ 폰이 붙은 대역의 서버로
  → 서버: ssh <폰> "pkill iperf3; nohup iperf3 -u -c 192.168.8.109 -p 5211|5212 -b 30M -l 1400 -t 65 &"
  → 60초 뒤 서버 타이머가 정지 (iperf3 -t 65 는 이중 안전장치)
  → SSE load 필드로 화면 버튼 상태 동기화

3-3. 폰 위치 찾기 (비교 화면)

비교 화면이 4초마다 두 서버의 /check를 부른다. 각 서버는 자기 대역 SSH 이름(s21g 또는 s21)으로 폰에 접속을 시도하므로, 응답이 오는 쪽이 그 폰의 현재 대역이다. 어느 쪽도 응답이 없으면 "연결 안 됨"으로 버튼을 끈다.

3-4. 정답 비교 (패널)

서버가 SSE에 truth와 truth_src를 싣는다. 패널은 truth와 모델 원시 판정 raw_label을 같은 순간끼리 비교해 일치율과 색 띠를 그린다.

truth_src정답의 출처언제
occupancy (A안, 현재)라벨 공식의 점유율 축(40/55/75%)으로 낸 단계실시간. 업링크에선 정답 라벨의 95~100%가 점유율 원인이라 실측에 가깝다
csv수집 때 victim 프로브로 잰 실측 라벨재생 모드(--replay)
probe (B안, 예정)시연 중 victim 프로브 실측 (학습 라벨과 같은 정의)대역마다 victim 기기 1대 필요 (§11)

9. 설계 결정과 이유

결정이유
부하 = 업링크 (폰 → AP → 유선 Pi)노트북이 받으면 폰을 5GHz로 옮겨도 AP→노트북 구간이 노트북 대역(2.4GHz)에 남는데, Opal 점유율엔 AP 자신의 송신이 빠져 2.4GHz가 "여유"로 보이는 착시가 생긴다. Pi는 유선이라 부하가 폰이 붙은 대역에만 실린다. 또 업링크는 모델이 가장 잘 보는 부하(정답의 95~100%가 점유율 원인)다. 노트북 방향 데이터는 학습에 그대로 있다.
5GHz 40MHz80MHz면 폰 두 대(폰당 70M, 80M이면 AP CPU 크래시)로 점유율이 41%를 못 넘어 화면이 안 오른다. 2.4GHz도 HT40이라 같은 폭 비교가 공정하고, 5GHz 모델이 40MHz 데이터로 학습돼 조건이 맞는다.
서버 두 개AP는 두 대역을 동시에 켜 둔다. 대역마다 서버를 두면 코드는 그대로(--band만) 쓰고 서버 재시작 없이 두 대역을 동시에 보여 준다.
폰은 손으로 옮김Android는 앱이 와이파이 네트워크를 바꾸기 어렵고, Opal은 두 대역 SSID가 달라 AP 쪽 자동 이동(802.11v 밴드 스티어링)도 잘 안 된다. 시스템은 원래 "전환 후보를 제시하고 실행은 하지 않는다"로 설계됐다(Opal 불안정). 현장 자동화는 AP 표준 기능(같은 대역 채널 이동 = 802.11h CSA, 다른 대역 = 밴드 스티어링)이 맡는다.
정답 A안(점유율 축)실측 정답(victim 프로브)은 victim이 그 대역에 붙어 있어야 해서 두 대역 동시 표시엔 victim 2대가 필요하다. 업링크에선 점유율 축이 실측과 97~100% 같다. 패널은 truth_src로 B안을 그대로 받게 만들어 두었다.
"AP 응답 없음" 15초부하 중 폴링이 몇 초 늦어지는 것만으로 6초 기준에 걸려 10번 깜빡였다 → 15초로 늘리고 0번.

부하 방향 다섯 가지(노트북·폰↔폰·업링크·다운링크·혼합)를 흐름도로 비교한 그림은 final_model_24sess.html §0 "흐름도" — 어느 구간이 점유율에 잡히고 어느 구간이 안 잡히는지 색으로 구분했다.

같은 날 자유 시험에서 5GHz 30M에도 전환 경보가 2번 떴다 — 원시 심각 4/138(3%), 전부 점유율 69~70%(점유율 기준 정답은 혼잡)로 혼잡↔심각 경계에서 한 단계 높게 본 것. 그리고 부하 없이 2.4GHz 점유율이 40~80%로 튀어(이웃 공유기·간섭원 추정, AP ch1 사용률 76.6%) 모델이 심각·경보를 냈다 — 라벨 기준상 맞는 판정이다.

학교는 2.4GHz 배경 점유율이 높아(랩실 idle 45~50%) 같은 30M에도 심각이 더 쉽게 날 것으로 본다. 반대로 5GHz는 거리에 민감해서 폰을 멀리 두면 점유율이 올라간다.

11. 한계와 다음

  • 다운링크는 약하다 — Opal 점유율이 AP 자신의 송신을 빼서 다운링크 혼잡이 안 보인다(다운링크 심각 recall 0~7%). 화면은 "판단 불확실"을 띄운다. 데모 부하엔 다운링크 방향(iperf3 -R)을 아직 안 넣었다.
  • 정답 B안 — 2.4GHz victim(노트북) + 5GHz victim(3번째 기기) + Pi 프로브 에이전트 + 서버 정답 계산(앵커·max·실패=max·k2m2). 폰을 victim으로 쓰면 와이파이 절전 때문에 노트북 victim과 수치가 다를 수 있어 먼저 나란히 비교 시험(라벨 일치 90% 이상이면 사용).
  • 노트북은 부하 경로 밖이어도 정답·입력에 들어간다 — 수집 때 정답의 손실·지연·지터 축은 Pi가 노트북에 보낸 victim 프로브·ping으로 쟀다(모든 부하 방향 공통, 노트북 위치가 라벨에 반영). 모델 입력도 AP에 붙은 기기 전체 기준이라 RSSI 3종은 노트북 포함 평균이고, 전송 속도·재전송 비율엔 AP가 노트북에 보낸 victim 스트림 몫이 섞인다 — 학습 땐 노트북이 늘 그 대역에서 victim 스트림을 받고 있었다. 시연엔 victim 스트림이 없고 노트북은 한 대역에만 붙으므로, 다른 대역은 "노트북 없이 폰만"인 학습과 조금 다른 조건이 된다(10-06 리허설에선 점유율 기준 일치 90%/97%로 문제는 안 보임). B안(대역마다 victim 기기)을 하면 정답이 실측이 될 뿐 아니라 이 입력 조건도 학습과 같아진다. 흐름도는 final_model_24sess.html §0.
  • AP 크래시 — 폰당 80M 이상, 또는 신호가 크게 비대칭이면 위험(ap_crash_analysis). 시연 부하는 40M 이하.
  • 날마다·장소마다·채널마다 다르다 — 같은 30M에 5GHz가 ch36(10-06) 경고 92%, ch48(10-08) 경고·혼잡 섞임에 경계 경보 2회. 시연 전 채널 고정(발표장 ch44)과 당일 확인이 필요하고, 5GHz 경보가 신경 쓰이면 폰당 20M(5GHz 정상~경고)을 쓴다. 전환 규칙은 평가와 맞추려고 바꾸지 않는다.
  • 외부 혼잡은 조절할 수 없다 — 2.4GHz는 우리 부하 없이도 이웃 때문에 심각이 뜰 수 있다(10-08 관측). "현장 2.4GHz는 원래 붐빈다"는 근거가 되지만 시연 순서를 흔들 수 있어 재생 모드를 예비로 둔다.
  • 다음: 학교 현장 사전 점검, Opal에서 패널 실시간 확인, 실제 Pi 반영, (선택) Pi에서 서버 두 개 구동.
