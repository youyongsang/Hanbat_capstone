AP 트래픽 혼잡 분류 — Capstone 2026

혼잡 라벨 재설계 — 표준 앵커 + victim 프로브

2차 데이터(ap_metrics_v2_redesign2)의 congestion_score / label 정의와 그 근거. 옛 weighted-sum 정의(congestion_label_criteria)를 대체하는 현행 정본이다.

▸한 줄 요약 — 라벨 = victim 프로브(경량 UDP 스트림)의 실측 QoS + AP 채널 상태를 각각 국제 표준 문턱에 매핑한 뒤 max로 합친 값. 모델 입력에서는 프로브 파생값과 jitter_ms/latency_ms를 빼서, 모델이 "재지 못하는 victim QoS를 채널 상태만으로 예측"하게 만든다.
ℹ이 페이지는 정의·근거 중심. 세션별 캘리브레이션 로그·구현 순서·열린 항목 전체는 markdown 원본 docs/yongsang/congestion_label_redesign.md에 있다. 최신 수치는 .work-log/current.md.

01 왜 재설계했나 — 옛 정의는 순환논리

옛 정의: congestion_score = 0.20·throughput + 0.45·occupancy + 0.20·retry + 0.15·jitter, 문턱 0.25 / 0.50 / 0.75.

  • 심각이 사실상 channel_occupancy ≈ 100%에서만 나왔다. occ 66%면 나머지 축이 다 최대여도 산술적으로 0.75를 못 넘음.
  • → label 3 학습 데이터가 전부 "occ≈100" 순간 → 모델이 "occ 높음 → 심각" 지름길만 학습.
  • → 정답 라벨 자체가 occupancy 문턱과 거의 같음 → "occupancy 문턱 대비 LSTM이 낫다"를 증명할 수 없음 (비교 대상이 정답과 동일).
  • 가중치 occ 0.45도 우리 데이터의 label 2 vs 3 차이가 가장 큰 축이라 크게 준 것 — 외부 근거 아닌 자기 데이터 fit.

재설계 원칙

  • 1. 축별 문턱은 외부 표준에서 (ITU-T, Cisco/WLAN 가이드). 자기 데이터 fit 금지.
  • 2. 조합은 max — 표준은 "각 축이 언제 나쁜가"만 주고 "어떻게 합치나"는 안 줌. max면 가중치 논쟁 원천 봉쇄. 심각 = 최소 한 축이 표준 심각 문턱 돌파.
  • 3. 라벨 입력 ≠ 모델 입력. 라벨은 victim QoS(프로브) 실측에 의존, 모델은 프로브를 못 봄 → "채널 상태로 victim QoS 예측"이 모델의 일.

02 victim 프로브

QoS에 민감한 작고 일정한 스트림 하나(300kbps UDP)를 배경 부하와 별개로 흘리고, 그 스트림 자체의 jitter/loss를 측정한다. "이 혼잡 속에서 VoIP 통화 한 통이 얼마나 깨지나" — 합성 점수가 아니라 실제 앱 피해. 300kbps라 아무것도 못 막는다(센서지 부하 아님).

── 부하 (혼잡 유발) ──
  폰 191 ──iperf3 -u -b 25M──┐
  폰 S26 ──iperf3 -u -b 25M──┤──> AP ──무선──> 노트북 (부하 싱크)
                             │
── 프로브 (QoS 피해 측정) ──
  파이 ──iperf3 -u -b 300k -l 200──> AP ──무선 downlink──> 노트북 (프로브 싱크)
        지속 스트림, 파이가 구간별 jitter/loss 읽음
  • 파이→AP는 유선이지만 AP→노트북 홉이 무선이라 프로브가 폰들의 혼잡을 실제로 겪는다.
  • 300kbps·200B ≈ 187pps → VoIP급. 새 컬럼 probe_jitter_ms, probe_loss_pct.
  • latency_ms(ping RTT)는 유지 — iperf3 UDP는 RTT를 못 줌.

03 sub-score 표준 문턱 (앵커)

각 축을 4개 앵커에 piecewise-linear 매핑, [0,1] clamp. 구현: collect_metrics.py의 ANCHORS + anchor_score().

경고 0.25혼잡 0.50심각 0.75완전 1.0

라벨 축 (4개) — congestion_score = max(이 4개)

표준 원문 대조 완료 (2026-08-31). 심각(0.75) 앵커는 표준이 직접 지지, 경고·혼잡 앵커는 Cisco Enterprise QoS voice 값 또는 그 아래 보간(정식 표준 아님).

04 조합 = max

congestion_score = max(
    occupancy_score,   # 채널 airtime
    jitter_score,      # 프로브 IPDV
    loss_score,        # 프로브 패킷 손실
    latency_score,     # ping RTT/2
)   # retry·throughput은 제외

label = 0  if score < 0.25       # 정상
        1  if score < 0.50       # 경고
        2  if score < 0.75       # 혼잡
        3  if score ≥ 0.75       # 심각
▸심각 = 최소 한 축이 발표된 심각 문턱을 넘었다.
occupancy ≥ 75% (Aruba) OR 프로브 jitter ≥ 50ms (Y.1541) OR 프로브 loss ≥ 5% (Cisco QoS) OR ping 편도 ≥ 150ms = RTT ≥ 300ms (G.114).
심사 방어: "이 라벨 왜 이렇게?" → "각 축을 국제 표준 문턱에 매핑하고, 하나라도 넘으면 심각으로 봤다. 가중치는 없다."

max가 놓치는 것 (알려진 단순화)

여러 축이 "어중간하게 나쁜"(다 0.6대) 경우 각각은 혼잡에 머문다. 실제론 한 축만 0.8인 것보다 나쁠 수 있음. 대안(나중에): 비정규화 p-norm(p≈6, magic number 부담) 또는 app 축만 ITU-T G.107 E-model(R-factor)로 조합(정석, 무거움). 지금은 max로 시작.

실패 = max

프로브·ping 타겟이 같은 무선 다운링크를 타므로, 채널이 심하게 포화되면 프로브 완료 불가 / ping 무응답이 된다. 원래는 이 축을 0.0으로 처리 → 라벨이 조용히 occupancy 단독으로 되돌아감(재설계 목적 훼손). 수정:

channel_active = throughput ≥ 3 Mbps  OR  occupancy ≥ 40%
ping_hard_fail  = channel_active AND latency(3-폴링 median) == 0   → latency_score = 1.0
probe_hard_fail = channel_active AND 프로브 ever_ok AND 지금 stale  → loss_score    = 1.0
  • 왜 채널 포화로 보나: 이 판정에 도달했다는 건 유선 SSH로 AP 텔레메트리를 방금 정상 파싱했다는 뜻 — AP는 살아있고 무선 채널만 막힌 것.
  • idle 안전장치: channel_active 게이트 + ever_ok 게이트 (무부하 셋업 문제를 혼잡으로 오인 안 함).

05 모델 입력 feature 재정의

문제: max(표준 문턱)은 그 자체로 규칙 기반 분류기다. 배포 시점에 규칙으로 계산하면 되는데 왜 LSTM인가?

▸답: 프로브가 배포 시점엔 없다. 배포 시스템엔 victim 프로브(협조 싱크 + 지속 스트림)가 없다. 모델은 AP-side 텔레메트리만 보고 "지금 victim QoS가 깨지고 있는가"를 예측해야 한다. 규칙으로 못 한다 — victim 측정값이 없으니까. + 시계열 추세(window 10) + Early Exit 효율.

반론 검토: "공장 장비가 자기 지연율을 이미 안다면?" (2026-09-13)

실제 공장 자동화 장비가 자기 지연(cycle time/RTT)을 이미 로깅한다면, victim 프로브 없이 그 값을 직접 받아 규칙으로 계산하면 되는 것 아닌가 — 그럼 LSTM(나아가 모델 자체)이 무의미해지는 게 아닌가? 결론: 전제는 부분적으로 맞지만, 그래서 이 프로젝트가 무의미해지진 않는다.

  • 유선 산업 프로토콜은 실제로 지연 진단을 갖고 있다. PROFINET RT/IRT는 250µs~1ms급 결정적 사이클타임을 스펙으로 갖고, OPC UA도 subscription publishing interval·네트워크 RTT·서버 publish cycle을 조합해 지연을 진단하며 TSN 환경에선 RTT/jitter가 실시간 성능 지표로 명시돼 있다 (Real-Time Performance of OPC UA, arXiv:2310.17052; PROFINET University).
  • 그런데 이건 대부분 유선 필드기기·컨트롤러용이다. AP가 관리하는 건 무선 클라이언트(핸드헬드 스캐너, 무선 센서, 이동 로봇, 태블릿)인데, 이런 기기 대부분은 PROFINET/OPC UA 스택을 안 돌린다 — 지연 데이터가 어딘가엔 있어도 AP·Pi까지 도달하지 않는다.
  • 한 클라이언트의 지연율만으론 "채널 전환" 판단이 안 된다. 목표는 채널을 공유하는 전체의 상태 파악인데, capture effect(ap_crash_analysis — 신호 강한 기기가 채널 독점·약한 기기가 굶는 현상)처럼 클라이언트마다 체감이 다르다. 이질적 무선 기기 전부의 표준화된 협조 보고는 실전에서 비현실적.
  • 그래서 실제 연구도 AP-side 텔레메트리만 쓰는 접근을 택한다. APDT(Access Point Digital Twin)는 신호세기·트래픽량·throughput·패킷손실 같은 AP-side 신호만으로 혼잡도 예측 모델을 학습하고(arXiv:2511.23009), 대학 건물 AP 100개 실측으로 LSTM/CNN/GRU/Transformer를 비교한 연구도 마찬가지로 AP 관측만 사용한다(arXiv:2408.09423).
ℹ결론: "유선 장비 일부가 지연율을 안다"가 "무선 클라이언트 전체가 협조한다"를 의미하지 않는다. 이 프로젝트의 전제(AP만 보고, 클라이언트 협조 없이 판단)는 유선 자동화 프로토콜의 존재와 무관하게 유효 — 오히려 이 문제가 왜 어렵고 의미 있는지 보여주는 근거가 된다. (특정 배포 현장의 클라이언트 전부가 실제로 협조 보고한다면, 그 현장에 한해 보너스 입력으로 추가하는 건 별개로 이득일 수 있음 — 일반해를 대체하는 게 아니라 특수해를 더하는 것.)

남는 관측 한계를 넘는 법: Early-Exit 스타일 능동 프로브 트리거 (하이브리드 아키텍처) (2026-09-14)

"AP만 보고 판단"이라는 전제는 정당화됐지만 대가로 남는 관측 한계는 실재한다 — 라벨 3(심각)의 78.2%가 occupancy가 아닌 축(주로 loss, 83%)이 원인인데 모델은 그 축을 못 본다. 이 한계는 일부는 하드웨어 세대 문제(nl80211 airtime_link_metric을 상위 MediaTek 칩만 펌웨어 레벨에서 지원, 지금 AP인 MT7621A는 없음)이고 일부는 보편적 한계(victim이 실제로 패킷을 받았는지는 결국 받는 쪽이 보고해야 완벽히 알 수 있음 — Wi-Fi 프로토콜 구조 자체의 문제라 AP 등급과 무관, 그래서 상용 솔루션도 소수의 능동 테스트 에이전트를 함께 씀).

제안 — Early Exit의 "확신 있으면 가볍게, 애매하면 더 본다"는 원리를 모델 레이어(exit1/2/3)뿐 아니라 파이프라인 전체(패시브 판단 vs 능동 프로브 발동)에도 적용한다: 확신 높으면(softmax 최대확률 ≥ θ) 패시브 판단 그대로, 확신 낮으면(< θ) 짧게(~2초) 능동 프로브를 발동해 실측 congestion_score로 확정.

배포 함의

  • "모든 클라이언트 협조" 대신 "협조 기기 1대 상시 배치 + 드물게(3~8%)만 짧게 찌르는 것"으로 완화 — 상용 제품(소수 지정 센서)과 같은 현실적 패턴. 단, 센서 "개수"(AP당 최소 1대)는 트리거율과 무관하게 그대로 필요 — 트리거율이 줄여주는 건 개수가 아니라 센서 1대당 운영 부담(전력·airtime).
  • 트리거된 ~2초 경로는 목표2(모델 추론 <1ms)와 무관한 별도의 드문 예외 경로 — 채널 전환이라는 물리적 동작 자체도 수 초~수십 초 걸림. 완전히 무해하진 않은 정직한 제한 사항(§8에 단축 아이디어 별도 기록).
  • 협조기기 후보(현실성 순): RPi Zero 2 W(완전한 Linux, 기존 ProbeRunner/iperf3 코드 재사용 가능, 저비용) > AGV/무선 스캐너 등 기존 무선기기 재활용(비용 0, 단 설치 권한 문제) > ESP32(최저가, iperf3 완전 호환 아님).
  • 센서는 상시 전원은 켜두되 유휴 대기만(iperf3 -s 리스닝 비용 거의 0) — 기기를 그때그때 깨우는 구조가 아니라 Pi가 필요한 순간에만 짧게 트래픽을 보내는 것뿐.
  • LSTM은 무의미해지지 않는다 — "전부 판단"에서 "92~97%는 직접 판단 + 확신도로 언제 프로브가 필요한지 결정하는 게이트키퍼"로 역할이 바뀔 뿐. 센서 1곳(좁은 시야)과 LSTM(AP 전체 station 종합, 넓은 시야)은 상호보완적 — capture effect처럼 센서 위치만 멀쩡하고 다른 station은 굶는 경우를 LSTM이 잡아냄.
▸"실시간" 주장과의 관계 — 목표2와 혼동 금지. 목표2(추론 <1ms)는 LSTM 모델 자체의 추론 시간에 대한 목표이지 최종 판단까지의 전체 시간이 아니다. 하이브리드를 얹어도 모델 계산 시간은 그대로 <1ms. 프로브 트리거는 목표1(정확도)을 위해 극히 일부 순간(3.4%)에만 의도적으로 실시간성을 내려놓는 별개의 메커니즘이다 — "시스템은 실시간으로 동작한다"(❌ 오해 소지) 대신 "모델 추론은 실시간을 유지하되, 애매한 3.4%는 의도적으로 실시간성을 희생하고 확인한다"(✅)로 서술.
ℹ채택 범위: 이 구조는 오프라인 시뮬레이션(실제 probe 정답값 + 5시드 재현)으로 검증된 제안·향후 연구로 채택한다. 실제 라이브 구현(프로브 컨트롤러 모듈, 협조기기 배치, 데모 연동)은 이번 학기 스코프 밖으로 보류 — 시뮬레이션만으로 충분히 방어 가능한 근거이고, 라이브 네트워크 작업은 예상 못 한 변수가 많으며(이번 세션의 "AP 크래시" 오판 사례 등), 남은 시간은 보고서 작성에 우선 배정. 상세·산출물: .work-log/current.md 25차 후속, project/.tmp/exp_l3_threshold/probe_trigger_simulation.py.

대안 경로: 새 AP 구매(per-station airtime) 재검토 (2026-09-14)

하이브리드는 대가(센서 의존성+지연)를 치르고 얻은 개선이라 "공짜"가 아니다. 대가 없이 순수 패시브 정확도 자체를 올릴 수 있는 새 AP 카드는 여전히 유효한 대안 — 단 불확실성이 커서 우선순위는 하이브리드보다 낮다.

  • per-station airtime이란: 채널 전체 점유율·station 평균 재전송률은 "채널이 얼마나 바쁜가"만 알려주고 "어느 station이 밀리는가"는 모른다. per-station airtime은 기기(MAC)별로 실제 전송 기회를 얼마나 받았는지 직접 재는 값 — capture effect(신호 강한 기기가 채널 독점, 약한 기기가 굶는 현상)를 추론이 아니라 직접 관측 가능하게 함. 굶는 정도가 심해지면 패킷이 드롭(=loss)되므로 기존 sta_tx_bitrate_min보다 loss와 더 직접 연결될 가능성. feature 아이디어: 같은 패턴으로 sta_airtime_min(연결된 station 중 최솟값) 추가 — 미검증, 향후 연구.
  • 칩셋 vs OpenWrt 구분(중요): 이 정보가 없는 건 OpenWrt의 한계가 아니라 칩셋+드라이버의 한계 — OpenWrt는 SSH·iw 접근이라는 "문"만 열어줄 뿐, 그 문 안의 내용(어떤 통계를 nl80211에 채우는지)은 칩셋이 정한다. 지금 AP(MT7621A, 구형·저가)는 방이 휑하고, 상위 칩(MediaTek MT7996, WiFi 7 플래그십)은 펌웨어 MCU 레벨에서 station별 airtime을 준다는 기록 확인(단 중급인 MT7981 — 원래 계획한 GL-MT6000의 칩 — 지원 여부는 미확인, MT7996은 한 단계 위).
  • MT7996 탑재 후보(OpenWrt 지원까지 별도 확인 필요): GL.iNet Slate 7 Pro(GL-BE10000)·Flint 3(GL-BE9300), Banana Pi BPI-R4(OpenWrt/mt76 지원 커뮤니티 문서로 명시 확인됨).
  • 10배 데이터로 우회 가능한가 — 아니다: 22차에서 이미 애매한 구간(occ 40~74)을 정확히 겨냥해 60% 더 모았는데도 회색지대 정확도가 8%→9%로 사실상 그대로였음 — 표본 부족이 아니라 "같은 7개 입력값이 다른 순간엔 다른 라벨(loss 때문)"이라는 irreducible error 구조라는 근거가 이미 있음. 10배는 이 AP로 수 주~수개월 걸려 이번 학기 내 시도 자체가 불가능.
ℹ새 AP는 "진짜 새로운 축(per-station airtime)을 주는가"에 전부 달려 있고, 오늘 3번 실패한 "그럴듯해 보였지만 같은 정보의 재탕" 패턴과 다를 가능성은 있으나 사서 실측하기 전까진 확정 불가. 이번 학기엔 하이브리드(검증 완료)가 우선, 새 AP는 여력 되면 시도할 향후 연구.
