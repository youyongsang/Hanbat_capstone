AP 크래시 원인 분석

label 3(심각) 데이터를 더 모으려고 여러 부하 조합을 시도하며 관찰한 GL.iNet Opal(GL-SFT1200) 크래시 패턴을 정리한다. 가설을 두 번 정정했다.

현재 결론: "몇 대가 붙어있는가"가 아니라 "누가 능동적으로 송신하는가"가 크래시의 핵심 변수였다. 노트북이 보내면 안정적이고, 폰이 보내면 거의 즉시 죽는다 — 목적지와 전송률은 상관없었다.

01 가설의 변화

두 번 정정했다. 매번 반례가 나와서 다음 가설로 넘어갔다.

기각
1차 — 잦은 재연결(reconnect churn)이 원인이다

UDP 손실률을 계속 갱신하려고 2~5초마다 iperf3를 재접속시켰는데, 이게 AP에 부담을 준다고 생각했다. 재연결 루프를 완전히 제거한 시도(2대, 100Mbps)도 여전히 ~22초 만에 크래시해서 기각.

기각
2차 — 동시 station이 2개 이상이면 크래시한다

3대/2대 조합은 전부 20~60초 안에 죽었고, 1대만 쓴 시도는 훨씬 오래 버텼다. 그런데 "폰 1대(무선)→파이(유선)"는 station이 똑같이 1개인데도 거의 즉시 크래시했다. station 개수만으로는 설명이 안 됨.

현재
3차 — 폰이 능동적으로 송신할 때 크래시한다

노트북이 송신자면 목적지·전송률 무관하게 안정적(150Mbps까지 확인). 폰이 송신자면 목적지·전송률 무관하게 거의 즉시 크래시. 아래 §02 참고.

04 부가 발견 — 유선 구조는 안전하지만 label 3을 못 만든다

노트북→파이 150Mbps 시도에서 channel_occupancy가 100%까지 여러 번 찍혔는데도 congestion_score는 문턱을 못 넘었다.

노트북→파이(유선) 최고 기록
0.646
왜 이런 일이 생기나

congestion_score의 45%는 occupancy가 담당하지만 나머지 55%(throughput+retry+jitter)도 같이 높아야 0.75를 넘는다. 유선 목적지는 무선 충돌·재전송이 거의 없는 "깨끗한" 경로라 retry_failed_score·jitter_score가 낮게 유지된다 — 그래서 occupancy가 100%여도 전체 점수가 문턱을 못 넘는다.

→안전성(노트북 송신)과 label 3 생성 능력(무선 경합 필요)이 트레이드오프 관계다. 지금까지는 폰이 송신해야만 label 3급 재전송/지연 변동이 나왔는데, 그게 바로 크래시를 유발하는 조건이기도 하다.

05 다음 검증 방향

  1. 다른 폰(221)으로 교체해서 재현 여부 확인재현 안 되면 191 폰 특정 문제, 재현되면 AP의 폰-일반 호환성 문제로 원인이 좁혀진다.
  2. 폰 송신을 훨씬 낮은 전송률(10~20Mbps)로 재시도지금까지 폰 송신은 항상 40Mbps 이상이었다 — 더 약하게 걸어도 즉시 죽는지 확인 필요.
  3. 채널폭 제한(2.4GHz 또는 5GHz 20MHz)과 병행낮은 전송률로도 점유율을 쉽게 포화시켜, 폰 송신 부담을 줄이면서 label 3을 노려본다.
  4. 호중에게 이 분석 공유펌웨어 업데이트 여부나 대체 장비 확보 가능성 문의.
