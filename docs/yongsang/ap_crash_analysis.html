AP 크래시 원인 분석

label 3(심각) 데이터를 더 모으려고 여러 부하 조합을 시도하며 관찰한 GL.iNet Opal(GL-SFT1200) 크래시 패턴을 정리한다. 가설을 다섯 번 정정했다.

최신 결론(8/27): 한때 "몇 대가 동시에 붙어있는가"(다중 station)가 핵심 변수로 재확정됐으나, 8/26 저녁~밤 세션에서 같은 콤보 조합이 어떤 날은 크래시하고 어떤 날은 5~7분씩 깨끗하게 완주했고 그 차이가 "시작 전 두 폰의 와이파이를 재연결했는가"와 강하게 상관됐다. 그래서 실제 변수는 개별 폰의 와이파이 연결 상태 / Wi-Fi capture effect(신호가 강한 S26이 채널을 독점, 신호가 약한 191이 굶는 비대칭)로 재해석됐다. 스위트스팟은 191=60M/S26=60M(2~7분)이 기준선이고 75M/75M 대칭도 label 3 후보로 떠올랐다(재현성 불완전). 상한은 확실하다 — 80/80은 10분에서 완전 크래시, 60/60도 500초를 넘기면 완전 크래시(안전 구간 대략 300~420초). 8/27 세션엔 실기기 없이 SSH 폴링 자기참조 지연을 지속 SSH 세션(APPoller)으로 전환하는 코드 조치를 했다(미검증).

01 가설의 변화

다섯 번 정정했다. 매번 반례가 나와서 다음 가설로 넘어갔다.

기각
1차 — 잦은 재연결(reconnect churn)이 원인이다

UDP 손실률을 계속 갱신하려고 2~5초마다 iperf3를 재접속시켰는데, 이게 AP에 부담을 준다고 생각했다. 재연결 루프를 완전히 제거한 시도(2대, 100Mbps)도 여전히 ~22초 만에 크래시해서 기각.

기각
2차 — 동시 station이 2개 이상이면 크래시한다

3대/2대 조합은 전부 20~60초 안에 죽었고, 1대만 쓴 시도는 훨씬 오래 버텼다. 그런데 "폰 1대(무선)→파이(유선)"는 station이 똑같이 1개인데도 거의 즉시 크래시했다. station 개수만으로는 설명이 안 됨.

약화
3차 — 폰이 능동적으로 송신할 때 크래시한다

노트북이 송신자면 목적지·전송률 무관하게 안정적(150Mbps까지 확인). 191 폰이 송신자면 목적지·전송률 무관하게 거의 즉시 크래시했다. 아래 §02 참고. 그런데 §06에서 다른 폰(S26)으로는 재현되지 않아, "폰이면 다 위험하다"는 일반화는 유지하기 어려워졌다.

반증
4차 — 191 폰 개별 하드웨어/드라이버 문제였을 가능성

같은 조건(station 수·목적지·전송률)에서 S26은 안정적이었기에 유력해 보였다. 하지만 오후 세션에서 191을 40M→70M→100M→120M→150M 다섯 단계 연속으로 돌려도 크래시가 한 번도 안 났다 — 오히려 label 3을 S26보다 훨씬 잘 만들어냈다. 이 5단계 연속 생존 자체가 "191 개별 문제" 결론과 정면으로 배치되어 반증에 가깝게 뒤집혔다.

약화
5차 — 다시 "몇 대가 동시에 붙어있는가"(다중 station)가 핵심 변수

S26/191 둘 다 단독으로는 40~150Mbps까지 완주했지만 191+S26 동시 부하에서만 불안정성이 나타났다. → 그런데 8/26 저녁~밤 세션에서 같은 콤보 조합이 어떤 날은 크래시하고 어떤 날은 5~7분씩 깨끗하게 완주했고, 그 차이가 "두 폰의 와이파이를 시작 전에 재연결했는가"와 강하게 상관됐다. 아래 §07~§11 참고.

현재
6차 — 개별 폰의 와이파이 연결 상태 / Wi-Fi capture effect

콤보 불안정성의 실제 변수는 "몇 대인가"보다 각 폰이 AP 와이파이에 제대로·대칭적으로 붙어있는가로 보인다. 신호가 강한 S26이 채널을 거의 독점하고 신호가 약한 191이 굶는 비대칭(capture effect)이 반복 관측됨 — 191은 ping 지연이 S26보다 계속 크고 불안정했다(RSSI 열세 추정). 여기에 "부하가 80/80 이상이거나 500초 이상 길면 그와 무관하게 완전 크래시"라는 상한 조건이 겹친다. 아래 §09~§11 참고.

04 부가 발견 — 유선 구조는 안전하지만 label 3을 못 만든다

노트북→파이 150Mbps 시도에서 channel_occupancy가 100%까지 여러 번 찍혔는데도 congestion_score는 문턱을 못 넘었다.

노트북→파이(유선) 최고 기록
0.646
왜 이런 일이 생기나

congestion_score의 45%는 occupancy가 담당하지만 나머지 55%(throughput+retry+jitter)도 같이 높아야 0.75를 넘는다. 유선 목적지는 무선 충돌·재전송이 거의 없는 "깨끗한" 경로라 retry_failed_score·jitter_score가 낮게 유지된다 — 그래서 occupancy가 100%여도 전체 점수가 문턱을 못 넘는다.

→안전성(노트북 송신)과 label 3 생성 능력(무선 경합 필요)이 트레이드오프 관계다. 지금까지는 폰이 송신해야만 label 3급 재전송/지연 변동이 나왔는데, 그게 바로 크래시를 유발하는 조건이기도 하다.

05 추가 검증 (아침 세션) — 다른 폰(S26)으로 교체하니 재현 안 됨

새로 구매한 폰 S26(192.168.8.103)을 송신자로 세워 §01의 3차 가설을 재검증했다.

→ station 수(2대, 노트북+S26)·목적지(이 노트북, 무선)·전송률(20→40Mbps)이 이전 191 폰의 즉시 크래시 조건과 비슷했는데도 20Mbps 120초, 40Mbps 90초 모두 완주했고 물리적 재부팅이 필요한 크래시는 없었다. 40Mbps 구간에서 AP가 SSH 폴링에 ~30초 응답 지연을 보인 적은 있지만, station 연결은 유지된 채 자연 복구됐다 — 예전의 "SSID 자체가 증발" 패턴과는 다른 경미한 증상이다.
→ 해석 갱신: "폰이 능동적으로 송신하면 크래시한다"는 3차 가설이 S26에서는 재현되지 않았다. "191 폰 개별 하드웨어/드라이버 문제였을 가능성"이 "폰 송신 자체가 위험"이라는 가설보다 유력해졌다. 다만 70~100Mbps 이상 고부하에서도 S26이 계속 안정적인지는 아직 확인 전이라, 완전히 확정하기엔 이르다.

09 추가 검증 (8/26 새벽) — 500초로 늘렸다가 진짜 완전 크래시, 안전 구간 상한 확인

이 노트북에서 iperf3 서버와 collect_metrics.py를 직접 기동/종료하며 60/60 콤보를 5회(rep6~rep10) 반복했다.

→rep6~rep9(300초 목표, 실제 4~6분대)는 전부 완주 — AP 크래시 없음, SSH 정상. label 3은 회당 1~4개로 여전히 흔들림(rep6 3 · rep7 3 · rep8 1 · rep9 4).
→rep10에서 지속시간을 500초로 늘려봤다가 진짜 완전 크래시가 재현됨: throughput이 84.86Mbps에서 급격히 붕괴 → retry_delta 10,935→33,288→39,060으로 폭주 → latency/jitter 0으로 죽음 → SSH 완전 타임아웃(ping 100% loss, 자연 복구 안 됨, 물리 재부팅 필요). 8행에서 중단. 60/60 스위트스팟의 안전 구간은 무한정이 아니라 대략 300~420초까지로 보인다.

14 부하 생성 방법 대안 — 소패킷 + RF 환경 열화 (2026-08-27 논의, 미실험)

연결되는 상위 질문: 이 프로젝트가 답해야 하는 건 "occupancy만으로는 안 잡히는 혼잡(경합·간섭·재전송 주도)을 조기종료 LSTM이 얼마나 정확히 잡는가"다(congestion_label_redesign.{md,html} §1·§3, 실측 대조는 ap_v2_redesign2_threshold_comparison_k3m2_archived_20260902.txt(k3m2 시절 마지막 실행, k2m2로 재실행 안 함)). 현재 label 3 샘플이 거의 다 occupancy=100% 순간이라 모델이 지름길만 학습했을 수 있다 — 아래 방법들의 목적은 occupancy가 아니라 retry/jitter가 주도하는 label 2/3 샘플을 확보하는 것이다.

현재 부하는 "다중 기기 × iperf3 -u -b ??M(기본 ~1470B UDP 프레임)"뿐이다. 한계: (1) occupancy는 100%까지 포화되는데 retry/jitter가 같은 순간에 안 터져서 label 3이 문턱을 못 넘는다, (2) 부하를 키우면 AP가 크래시한다(80/80·500초 확정).

핵심 재해석: 목표는 "낮은 throughput"이 아니라 높은 PPS·airtime + 열악한 RF 환경이다. 실험실은 RF가 깨끗해서 재전송이 안 생기는데, 실제 공장은 금속·다중경로·용접 EMI·밀집 AP 때문에 훨씬 낮은 부하에서도 retry/jitter가 터진다 — lab에서 label 3이 안 나오는 근본 이유다. 따라서 (a) 프레임을 잘게 쪼개 PPS↑, (b) RF 환경을 의도적으로 나쁘게 만든다. 채널 크리플(2.4GHz 강제 등)은 배포 regime과 안 맞아 지양. throughput_mbps가 낮아지는 건 무해(§07 — throughput_score는 label 2/3 변별력 없음).

!Opal은 소비자용 AP다. 크래시 천장(80/80·500초)은 물리 법칙이 아니라 GL-SFT1200의 한계다. 현실적인 데이터가 목적이면 더 나은 산업/기업용 AP 확보(호중 문의)가 정공법이고, 아래 방법들은 그 사이 label 3 표본을 보충하는 augmentation이다.
