01 문제: Early Exit이 오히려 느렸다

02 원인: LSTM 재계산이 아니라 세션 호출 오버헤드

"작은 모델일수록 손해가 클 것"이라는 직관은 맞았다 — 다만 이유는 레이어를 다시 계산해서가 아니다. staged 방식은 중복 계산을 하지 않는다(stage2는 stage1의 hidden state를 이어받는다). 진짜 비용은 InferenceSession.run()을 여러 번 호출할 때마다 붙는 고정 오버헤드(스레드 동기화·Python-C++ 경계·텐서 할당)다. 이 모델은 hidden_size=128로 작아서, skip해서 아끼는 연산량보다 그 호출 비용이 더 크다.

1차 — staged (세션 3개)
①
session1.run()lstm1 + classifier1
+ 세션 호출 오버헤드
②
session2.run()lstm2 + classifier2
+ 세션 호출 오버헤드
③
session3.run()lstm3 + classifier3
+ 세션 호출 오버헤드
exit3까지 가면 세션 호출을 3번 — 오버헤드도 3번.
2차 — unified (세션 1개)
①
session.run()lstm1 → If(entropy<θ₁) → lstm2 → If(entropy<θ₂) → lstm3
exit3까지 가도 세션 호출은 1번 — 그래프 내부에서 조건부로 skip.

03 해결: torch.jit.script → ONNX If 노드

torch.onnx.export의 레거시 경로는 파이썬 if문을 그대로 트레이싱하면 데이터 의존적 분기를 못 잡는다(한 번 실행된 경로만 그래프에 굳는다). torch.jit.script로 먼저 스크립팅하면 entropy 비교 if가 실제 제어 흐름으로 컴파일되고, 그 결과를 export하면 ONNX If 연산자로 나온다.

# project/scripts/export_onnx_ap_unified.py
class UnifiedEarlyExitFixed(nn.Module):
    def forward(self, x: Tensor) -> tuple[Tensor, Tensor]:
        out1, _ = self.lstm1(x)
        logits1 = self.classifier1(out1[:, -1, :])
        e1 = self._entropy(logits1)[0]
        if float(e1.item()) < self.theta_1:
            return logits1, torch.tensor(1, dtype=torch.int64)
        out2, _ = self.lstm2(out1)
        #  ... theta_2 조건도 같은 방식으로 이어짐

# 스크립팅 → export 순서가 핵심
scripted = torch.jit.script(wrapped)
torch.onnx.export(scripted, dummy_input, onnx_path, ...)

제약은 하나 — batch_size=1 전제다. 분기가 "이 한 샘플의 entropy"로 결정되니 배치 안에서 샘플마다 다른 exit을 타는 배치 추론에는 안 맞는다. 실시간 엣지 추론(윈도우 하나씩 순차 처리)이 목표라 문제없다. Dynamic θ 버전은 최근 occupancy 변화량으로 임계값을 조정하는 로직까지 같은 그래프 안에 스크립팅했다.

✓검증: PyTorch 참조 구현(infer_batch_stepwise) 대비 test 310창 전체에서 예측 라벨·exit_point 100% 일치(fixed·dynamic 둘 다 미스매치 0건).

07 후속 2차: "1학기 땐 됐었는데?" — 재확인 질문에서 원인을 다시 찾음

사용자가 1학기(4-feature) INT8 결과를 근거로 이 결론에 의문을 제기했다: 1학기 Pi 실측은 baseline 1.530ms → INT8 0.914ms(−40%), staged fixed 2.089ms → INT8 1.297ms(−38%)로 실제로 크게 빨라졌었다. 같은 도구를 쓰는데 왜 이번엔 이득이 없었을까?

# ONNX 그래프를 재귀적으로 순회해서 op 종류를 직접 셈
def walk(graph, counter, depth=0):
    for n in graph.node:
        counter[(depth, n.op_type)] += 1
        for attr in n.attribute:
            if attr.type == onnx.AttributeProto.GRAPH:
                walk(attr.g, counter, depth + 1)  # If 노드의 서브그래프까지 재귀
재귀 순회 결과 — unified 그래프를 양자화한 뒤 LSTM 노드 개수(깊이별)
깊이fp32 LSTM양자화 후 LSTM(float)양자화 후 DynamicQuantizeLSTM
0 (lstm1)110
1 (lstm2, If 서브그래프)110
2 (lstm3, 중첩 If 서브그래프)110
✗unified(If 포함) 그래프를 양자화하면 LSTM 3개가 전부 그대로 float로 남아있었다 — 제일 작은 classifier1의 Gemm 하나만 MatMulInteger로 바뀌어 있었다. 반면 ap_early_exit_fixed_stage1.onnx(제어 흐름이 없는 flat 그래프) 하나만 따로 양자화하니 LSTM이 정상적으로 DynamicQuantizeLSTM(진짜 int8 연산)으로 바뀌었다.
→진짜 원인: "모델이 작아서 양자화가 안 먹힌다"가 아니라, ONNX Runtime의 동적 양자화 도구가 If(제어 흐름) 노드가 있는 그래프에서는 LSTM 변환을 조용히 건너뛴다는 도구상의 한계였다. 1학기 때 실제로 빨라졌던 이유는 그때 그래프에 애초에 If 노드가 없었기 때문(staged 방식 = 단순 분리 = 매 stage가 flat 그래프)이다.

08 후속 3차: 양자화된 조각을 손수 재조립 — 두 마리 토끼를 다 잡음

세션 호출 오버헤드(1차 문제)를 피하려고 만든 단일 그래프가, 이번엔 양자화 도구의 발목을 잡은 셈이다. 해법은 순서를 바꾸는 것 — 양자화가 먹히는 flat 상태로 먼저 각 stage를 양자화한 뒤, 그 결과물을 If 노드로 손수 감싼다.

# project/scripts/export_onnx_ap_unified_int8_v2.py
# 1. staged(flat) 3개를 각각 독립적으로 양자화 — LSTM 정상 변환됨
quantize_dynamic(stage1.onnx, stage1_int8.onnx, op_types_to_quantize=["LSTM","MatMul","Gemm"])

# 2. 양자화된 조각을 onnx.helper로 직접 재조립
#    entropy/threshold/If 배선을 fp32 unified와 동일하게 재현
depth2_graph = make_graph(stage3_int8_nodes + [exit_point_const(3)], ...)
depth1_else  = make_graph(stage2_int8_nodes + entropy_nodes + [If(depth2_graph)], ...)
main_graph   = make_graph(stage1_int8_nodes + entropy_nodes + [If(depth1_else)], ...)

"Early Exit이 이 정도로 작은 LSTM에서는 latency를 못 줄인다"는 처음 결론은 staged(세션 분리) 배포 아키텍처에 국한된 이야기였다. 원인을 없애자 baseline 대비 40% 개선을 확인했고, 여기서 더 나아가 INT8 양자화까지 제대로 적용하면 baseline 대비 67%까지 줄었다 — 두 번 다 "모델/개념의 한계"처럼 보였던 게 실은 배포 파이프라인의 도구적 한계였다.

✓논문·보고서에는 단일 그래프 + INT8(stage별 양자화 후 재조립) 결과를 최종안으로 쓴다. fp32 unified는 안전한 대안, staged와 INT8 1차 시도는 지우지 않고 "왜 이 설계가 필요했는가"를 보여주는 동기/반례로 남긴다.
