# AP 트래픽 수집 코드 검토 및 보완사항

## 1. 검토 대상

- 대상 코드: 호중 AP 실측용 `collect_metrics.py`
- 실험 장비: GL.iNet Opal AP, Wi-Fi 클라이언트, 유선 서버
- 목적: AP를 통과하는 무선 트래픽의 혼잡 관련 지표를 CSV로 수집

## 2. 현재 코드의 장점

현재 코드는 1차 실측 코드로서 기존 방식보다 실험 구조가 개선되어 있다.

- `AP_IP`와 `SERVER_IP`를 분리하여 AP 상태 수집 대상과 트래픽 측정 대상을 구분한다.
- `iw dev wlan0 survey dump`를 사용해 채널 점유율을 수집한다.
- `iw dev wlan0 station dump`를 사용해 연결 클라이언트의 무선 링크 상태를 수집한다.
- `rx_bytes`, `tx_bytes`의 변화량을 이용해 AP 통과 트래픽 처리량을 계산한다.
- `tx_retries`, `tx_failed`를 누적값 그대로 저장하지 않고 이전 샘플과의 차이값으로 저장한다.
- 실행 시 `scenario`를 인자로 받아 부하 조건별 데이터를 구분할 수 있다.

따라서 현재 코드는 단일 Wi-Fi 클라이언트에서 부하 강도를 단계적으로 조절하는 1차 실측에는 적합한 구조이다.

## 3. 주요 아쉬운 점

### 3.1 채널 점유율 계산 방식

현재 코드는 `iw survey dump`에서 읽은 `channel busy time`과 `channel active time`을 바로 나누어 채널 점유율을 계산한다.

```text
channel_occupancy = busy / active * 100
```

하지만 해당 값이 AP 동작 이후 누적 카운터라면, 이 방식은 현재 순간의 채널 혼잡도보다 누적 평균에 가까운 값을 만들 수 있다. 이 경우 부하가 증가해도 채널 점유율 변화가 둔하게 나타날 수 있다.

권장 방식은 이전 샘플과 현재 샘플의 차이를 이용하는 것이다.

```text
channel_occupancy = busy_delta / active_delta * 100
```

### 3.2 jitter 미계산

CSV에는 `jitter_ms` 컬럼이 있지만 현재 코드는 항상 `0.0`을 저장한다.

Jitter는 지연시간의 변동성을 의미하며, 실시간 제어 또는 산업 무선망 안정성 판단에서 중요한 지표가 될 수 있다. 따라서 컬럼만 두는 것보다 실제 값을 계산해 저장하는 것이 좋다.

보완 방법은 다음 중 하나를 사용할 수 있다.

- `ping` 결과의 `mdev` 값을 jitter 대용으로 사용
- `iperf3 UDP` 결과의 jitter 값을 사용
- 일정 윈도우 내 latency 표준편차를 별도 피쳐로 생성

### 3.3 packet loss 기준

현재 `packet_loss_rate`는 `ping` 명령의 패킷 손실률을 사용한다.

Ping loss는 연결 상태 확인에는 유용하지만, 부하 실험에서는 대부분 0%로 유지될 수 있다. 실제 트래픽 부하에 따른 손실률을 확인하려면 `iperf3 UDP` 결과의 `lost_percent`를 함께 저장하는 것이 더 적절하다.

### 3.4 다중 클라이언트 처리

현재 실험 범위는 단일 클라이언트 정량 부하 실험으로 두는 것이 적절하다. 스마트폰과 태블릿은 부하량을 정량적으로 제어하기 어렵기 때문에, 다중 클라이언트 실험은 현 단계의 핵심 실험이 아니라 확장 가능 실험으로 분리하는 것이 좋다.

다만 향후 복수 노트북 또는 PC를 확보해 다중 클라이언트 실험을 수행할 경우, `iw station dump`의 여러 `Station` 블록을 클라이언트별로 처리해야 한다.

확장 시 필요한 처리 방식은 다음과 같다.

- `rx_bytes`, `tx_bytes`는 전체 Station 합산
- `tx_retries`, `tx_failed`는 전체 Station 합산 후 delta 계산
- `rssi`, `tx_bitrate`, `rx_bitrate`는 평균값 또는 최솟값으로 요약
- `connected_clients`는 Station 블록 개수로 저장

### 3.5 순간 링크 지표의 변동성

`rssi`, `tx_bitrate`, `rx_bitrate`는 순간 링크 상태를 나타내는 값이므로 샘플마다 흔들릴 수 있다. 모델 입력 피쳐로 사용할 경우 원본값만 사용하는 것보다 이동평균, 변화량, 최솟값 등으로 변환하는 것이 안정적이다.

## 4. 보완 우선순위

| 우선순위 | 보완 항목 | 이유 |
|---|---|---|
| 1 | 채널 점유율 delta 계산 | 순간 혼잡도 반영 |
| 2 | jitter 실제 계산 | 실시간 품질 변동성 반영 |
| 3 | UDP packet loss 수집 | 부하 상황의 손실률 반영 |
| 4 | 다중 Station 합산 로직 | 향후 다중 클라이언트 확장 대비 |
| 5 | 링크 지표 후처리 | 모델 입력 안정화 |

## 5. 현재 실험 범위 정리

현재 단계에서는 다중 클라이언트 실험을 핵심 실험으로 두기보다, 단일 클라이언트에서 부하 강도를 정량적으로 조절하는 실험을 우선 수행한다.

```text
1차 실험:
단일 Wi-Fi 클라이언트 + iperf3 부하 강도 조절

확장 실험:
복수 노트북/PC 확보 시 다중 클라이언트 부하 검증
```

스마트폰과 태블릿은 정량적인 부하 제어가 어렵기 때문에, 본 실험에서는 보조 부하 또는 향후 검증 항목으로만 활용한다.

## 6. 보고서 작성용 요약

현재 수집 코드는 단일 Wi-Fi 클라이언트의 정량 부하 실험에는 적합하지만, 채널 점유율의 순간 변화 반영, jitter 계산, UDP 손실률 수집은 추가 보완이 필요하다. 다중 클라이언트 실험은 스마트폰과 태블릿의 부하 제어가 어렵기 때문에 향후 복수 노트북 또는 PC 확보 시 확장 검증 항목으로 설정한다.
