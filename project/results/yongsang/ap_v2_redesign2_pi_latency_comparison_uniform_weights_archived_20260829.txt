=== 해석: Early Exit이 이번 Pi 실측에선 평균적으로 baseline보다 느림 ===
- exit1로 빠지는 샘플(29.7%)은 baseline보다 51% 빠름 — Early Exit의 latency
  이득 자체는 실재함.
- 하지만 exit2/exit3까지 가는 샘플은 별도 ONNX InferenceSession을 최대 3번
  순차 호출하는 구조라, 세션 호출당 고정 오버헤드(스레드 동기화·Python-C++
  경계·메모리 할당)가 매번 붙는다. 이 모델은 hidden_size=128로 작아서 LSTM
  레이어 자체의 연산량보다 세션 호출 오버헤드가 더 크다 — 그래서 exit3는
  baseline(그래프 1개, 세션 호출 1회로 전 레이어 계산)보다 오히려 57% 느림.
- 이번 test set은 라벨 분포가 어려운 편이라(§ap_v2_redesign2_eval_report.txt
  참고, L3 recall 51.6%) exit3 비율이 58.7%(fixed)/47.7%(dynamic)로 높다 —
  가중 평균이 baseline보다 나빠지는 조건이 갖춰짐.
- 결론: 이 모델 크기·이 test set 분포에서는 "그래프 1개, 매번 전체 계산"이
  가장 빠르다. Early Exit이 지연 이득을 내려면 (a) exit1 rate를 실질적으로
  올리거나(모델을 더 단순한 조기 신호에 민감하게 재조정) (b) staged 세션을
  하나의 ONNX 그래프 안에서 조건부 실행(If 연산자)으로 합쳐 세션 호출
  오버헤드를 없애는 재설계가 필요. 지금 구조(세션 3개 분리)는 개념 검증
  (레이어를 실제로 skip할 수 있다는 것)에는 유효하지만, 이 배포 구성 그대로는
  latency 승리를 주장할 수 없음 — 1학기 4-feature 모델(hidden_size 등 규모
  다름, project/results/hojung/)의 결과와 직접 비교하지 말 것.
- INT8 양자화는 이번 세션에 미실시 — 다음 단계 후보(연산량이 더 작아지면
  오히려 세션 오버헤드 비중이 더 커질 수 있어 반드시 도움된다는 보장은 없음,
  실측 필요).

2026-08-28 (같은 세션, 후속): 단일 그래프(ONNX If 노드) 재설계 — 성공
================================================================
`project/scripts/export_onnx_ap_unified.py`: `torch.jit.script`로 entropy 기반
조건 분기(if/else)를 캡처해서 `torch.onnx.export`가 ONNX `If` 노드를 내보내게
함. staged처럼 별도 세션 3개가 아니라 **하나의 ONNX 그래프, 세션 호출 1번**으로
early exit이 그래프 내부에서 일어남(batch_size=1 전제 — 실시간 단일 윈도우
추론용, 배치 추론엔 안 맞음).

정확도 검증: PyTorch staged reference(`infer_batch_stepwise`) 대비 test 310창
전체에서 **예측/exit_point 100% 일치**(fixed·dynamic 둘 다, 미스매치 0건).

결론(갱신): "이 모델 크기에서는 Early Exit이 latency를 못 줄인다"는 위 결론은
**staged(세션 3개) 구조에 한정된 얘기였고, 원인이었던 세션 호출 오버헤드를
없애자(단일 그래프+If 노드) Early Exit이 baseline 대비 40% 빠르다는 걸
실측으로 확인**. Early Exit 자체의 latency 가치는 정당했고, 문제는 배포
아키텍처였다. 논문/보고서에는 이 통합 그래프 결과를 "Proposed"로 쓸 것 —
staged 결과는 "왜 단순 분리가 아니라 단일 그래프 설계가 필요했는가"의
반례/동기로 남겨둔다.

2026-08-28 (같은 세션, 후속 2): INT8 동적 양자화 — 정확도 유지, 속도 이득 없음
================================================================
`project/scripts/export_onnx_ap_unified_int8.py`: `onnxruntime.quantization.quantize_dynamic`
(`weight_type=QInt8`, `op_types_to_quantize=["MatMul","Gemm","LSTM"]`)로 unified
그래프(fixed/dynamic)를 INT8 동적 양자화.

- **정확도**: fp32 unified 대비 test 310창 전체에서 예측·exit_point **0 mismatch**
  (fixed 88.4%, dynamic 89.0% — fp32와 완전히 동일). 정확도 손실 없음.
- **파일 크기**: 오히려 fp32보다 살짝 큼(1.374MB vs 1.365MB, fixed 기준) — 모델이
  작아서 압축 이득보다 양자화 메타데이터(scale/zero-point, DequantizeLinear 노드)
  오버헤드가 더 큼.
- **Pi 재측정**: fixed 1.204ms / dynamic 1.193ms — **fp32 unified(1.183/1.190ms)와
  오차 범위 내 동일, 속도 이득 없음.**

=== 최종 요약표 (모든 배포 방식) ===
방법                              avg(ms)  vs baseline   비고
Baseline(전체 그래프 1회)            1.966      —
Staged Fixed θ(세션 3개)             2.337     +19%       비권장
Staged Dynamic θ(세션 3개)           2.189     +11%       비권장
통합 Fixed θ(세션 1개, If, fp32)      1.183     -40%       **권장**
통합 Dynamic θ(세션 1개, If, fp32)    1.190     -39%       **권장**
통합 Fixed θ(세션 1개, If, INT8)      1.204     -39%       fp32와 동일, 이득 없음
통합 Dynamic θ(세션 1개, If, INT8)    1.193     -39%       fp32와 동일, 이득 없음

**(정정, 아래 "INT8 재시도" 섹션 참고)**: 위 결론은 틀렸다. 원인은 모델
크기가 아니라 **ONNX 양자화 도구가 `If`(제어 흐름) 노드가 있는 그래프에서
LSTM을 조용히 건너뛴다**는 도구상의 한계였다 — 재귀적으로 그래프를 뜯어보니
분류기(classifier1) 하나만 int8로 바뀌고 LSTM 3개는 전부 float로 남아있었다.
staged(제어 흐름 없는 flat 그래프)로 각각 양자화하면 LSTM이 제대로
`DynamicQuantizeLSTM`으로 바뀐다. 아래 섹션에서 이 양자화된 조각들을 손수
조립해 재시도한 결과, **실제로 큰 이득이 있었다**(unified fp32 대비 추가
-43~46%). 사용자가 "1학기 땐 실제로 좋은 결과가 나왔는데?"라고 재확인 질문을
준 덕분에 오류를 발견했다.

2026-08-28 (같은 세션, 후속 3): INT8 재시도 — 원인 재진단 + 그래프 재조립으로 해결
================================================================

**재진단**: `ap_early_exit_fixed_stage1.onnx`(제어 흐름 없는 flat 그래프) 하나만
따로 양자화했더니 LSTM이 `DynamicQuantizeLSTM`으로 정상 변환됐다. 반면
`ap_early_exit_fixed_unified.onnx`(If 노드 포함) 전체를 양자화하면 LSTM 3개
전부 원래 `LSTM`(float) 그대로였다 — ONNX 그래프를 재귀적으로 순회해서 op
목록을 직접 세어 확인. 즉 "모델이 작아서 양자화가 안 먹힌다"가 아니라
**"이 양자화 도구가 If 서브그래프 안의 LSTM은 변환하지 못한다"**가 진짜 원인.

**해결**: `project/scripts/export_onnx_ap_unified_int8_v2.py`(신규) —
1. `ap_early_exit_{fixed,dynamic}_stage{1,2,3}.onnx`(staged, flat) 각각을
   독립적으로 양자화(LSTM 포함 `quantize_dynamic`) → 이번엔 3개 다 정상적으로
   `DynamicQuantizeLSTM`으로 변환됨(확인 완료).
2. 양자화된 3개 조각을 `onnx.helper`로 손수 재조립 — entropy/threshold/If
   배선(Softmax→+eps→Log→Mul→ReduceSum→Neg→Gather(0)→Less(theta)→Cast→If)을
   fp32 unified 그래프와 동일하게 재현하고, 각 stage 내부 텐서 이름은
   충돌 방지를 위해 prefix. dynamic θ는 occupancy 변화량 기반 임계값 조정
   로직(`Slice`→`Gather`→`Sub`→`Abs`→`Greater`→`Where`)도 그래프 안에 재현.

**검증**: PyTorch 참조 대비 test 310창 중 **309개 정확히 일치**(fixed·dynamic
각각 1개만 경계값 근처 엔트로피 오차로 차이, int8 양자화 노이즈 수준).
정확도는 fp32와 동일(88.4%/89.0%).

**Pi 재측정**:

방법                              avg(ms)  vs baseline   vs unified fp32
Baseline(전체 그래프 1회)            1.966      —
통합 fp32 Fixed θ                   1.183     -40%
통합 fp32 Dynamic θ                 1.190     -39%
통합 int8(1차 시도, LSTM 미양자화)    1.204     -39%          +2% (이득 없음)
**통합 int8 v2 Fixed θ (LSTM 진짜 양자화)**   **0.641**  **-67%**   **-46%**
**통합 int8 v2 Dynamic θ (LSTM 진짜 양자화)** **0.679**  **-65%**   **-43%**

exit별 지연(fixed θ v2): exit1 0.288ms(baseline 대비 -85%) / exit2 0.569ms
(-71%) / exit3 0.832ms(-58%) — 모든 exit point에서 baseline은 물론 fp32
unified보다도 크게 빠르다.

**최종 결론 (갱신)**: 1학기 자료가 실제로 보여줬던 int8 이득(baseline -40%,
staged -38%)이 이번에도 재현 가능했다 — 처음엔 그래프 구조(If 노드) 때문에
막혀 있었을 뿐이다. **최종 배포 구성은 "단일 그래프 + INT8(stage별 양자화 후
재조립)"**로 확정. fp32 unified(1.18ms)는 "안전한 대안"으로, 1차 시도
int8(1.20ms, LSTM 미양자화)은 "실패 사례"로 기록에 남긴다.
